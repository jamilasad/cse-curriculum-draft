Purpose and why it exists

Grades in the earlier courses average many components, and from semester 2 lab work and assignments allow AI as a tutor (Level 1), so a student can pass every programming course with an uneven practical base, and take-home work is no longer reliable evidence of skill. CSE-2440 is the one point where the programme checks, unaided and in one sitting, that each student has the floor that the semester-7 track courses and the capstone assume: write a program, debug one, choose a data structure, query a database, work in a shell with Git, and read code. It replaces the end-of-programme general viva of the 2022 syllabus with a practical check two years earlier, while there is still time to close gaps. Tasks are set at the level a mid-level student reaches after semesters 1–3 with steady practice; this is not a ranking or a contest. The strong 15% should pass at the first sitting with time to spare. For the 60% in the middle it is the checked floor of framework principle 5, and for the weaker 25% the clinics, banked stations and six sittings before semester 7 give a route to the floor instead of a single cut-off.

Format and language rule

  • Six stations in one session. Block A: stations 1, 2 and 6 (95 minutes). Break of 20 minutes. Block B: stations 3, 4 and 5 (85 minutes). Each station opens and closes on the harness clock; unused time does not carry over.
  • At registration the student chooses one of Python, C++ or Java for stations 1, 2, 3 and 6 and uses it for the whole sitting. Specifications give input and output formats or function signatures for all three; debugging and code-reading tasks exist in all three versions. C is not offered, because station 3 expects standard-library containers. Station 4 is SQL and station 5 is Bash and Git for everyone.
  • Performance time limits are set per language, so the intended solution passes comfortably in each and the naive one fails in each.
  • Allowed: offline Python, C++ standard library and Java API documentation, manual pages, the language's debugger. Not allowed: notes, phones, any network access.
  • Statements are in short, plain English with one worked example each.

Stations and sample tasks

Station 1. Programming from a specification (45 minutes). One task needing about 40–80 lines, given as a statement, input and output formats and a worked example; marked by hidden tests.

  • Sample A: Read lines student_id course_code mark from standard input in any order. For each student, in ID order, print the number of courses, the average mark to one decimal place, and PROBATION if the average is below 50 or any mark is below 40. Blank lines are ignored.
  • Sample B: Given the day's university bus departure times (HH:MM, unsorted, possibly repeated) and a list of query times, print for each query the next departure and the minutes to wait, or NO BUS after the last one; a query exactly at a departure waits 0 minutes.

Station 2. Debugging an existing program (30 minutes). A 50–80 line program with three planted defects, at least one a logic error that gives wrong output without crashing, and visible failing tests. The student fixes the defects and writes one line per fix stating the cause.

  • Sample A: A library-fine calculator that counts overdue days with an off-by-one loop bound, loses the fractional part of the fine through integer division, and has one language-specific fault: strings compared with == in Java, an uninitialised accumulator in C++, a mutable default argument in Python.
  • Sample B: A word-frequency report that drops the last word of each line, counts Data and data separately, and orders ties wrongly when sorting by count.

Station 3. Choosing and using a data structure (35 minutes). A small visible input and large hidden inputs (a few hundred thousand operations) on which a list-scanning solution times out. The student uses standard-library containers and writes at most three lines naming the structure and the cost of the main operation.

  • Sample A: A help desk receives ARRIVE name priority and SERVE commands; each SERVE prints the waiting person with the highest priority, earliest arrival first among equals (priority queue with an arrival counter).
  • Sample B: For a stream of transaction IDs, print the position of every ID that already appeared among the previous k transactions (hash set plus a queue for the sliding window).

Station 4. SQL against a given schema (25 minutes). A schema diagram and a database with sample rows; four queries, marked by running them on a hidden database with the same schema and different rows. Scope is what CSE-2423 Database Systems has taught by week 9: selection and ordering, inner and outer joins, grouping with HAVING, simple subqueries, INSERT, UPDATE and DELETE.

  • Sample A: Tables student, course and enrolment(student_id, course_code, semester, grade_point). List a section's students by name; count enrolments per course in a semester, including courses with none; list students whose average grade point is below 2.50; raise grade points in one course by 0.25 without exceeding 4.00.
  • Sample B: Tables customer, product, orders and order_item. Revenue per month; customers who have never ordered; the three best-selling products by quantity; delete orders that have no items.

Station 5. Linux shell and Git (25 minutes). A prepared home directory and a Git repository whose remote is a local bare repository. A check script inspects the final state of files and repository; shell history is kept for review.

  • Sample A: In a folder of about 2,000 log files, count the files containing ERROR on a given date and write the count to report.txt; move every .csv file into data/; make run.sh executable; commit on a new branch fix-report with a meaningful message and merge it into main.
  • Sample B: Save in top5.sh one pipeline that prints the five most frequent IP addresses in access.log; use git log and git diff to find the commit that changed total_fee and undo it with git revert; resolve the supplied merge conflict keeping both changes; push to the remote.

Station 6. Reading and explaining unfamiliar code (20 minutes). A 30–50 line program with no comments and uninformative names, in the student's language. Five short questions: the exact output for a given input; the purpose of the main function in one sentence; an input that triggers a stated edge behaviour; the effect of changing one marked line; better names for two variables.

  • Sample A: A function that returns the length and start index of the longest run of equal adjacent values in a list.
  • Sample B: A stack-based checker that reports the position of the first unmatched bracket, with a fault when the string ends in an open bracket.

Overall pass: all six stations passed, in one sitting or banked across sittings, and the oral check confirmed for each sitting in which a station was passed. There is no compensation between stations; each is a floor. A "strong" band (all tests or all items) is recorded per station for feedback only. Borderline examiner-marked answers are second-marked.

Oral check of explanation

  • Every student who passes at least one station at a sitting has a 5-minute oral within three working days, on two of their own passed answers drawn at random by the harness (code stations preferred). The examiner opens the submission and asks the student to walk through it, to say what happens for an input the examiner names, and to make or describe one small change.
  • Outcome is Confirmed or Not confirmed. Not confirmed goes to a second examiner the same day; if still not confirmed, the station passes from that sitting are void. The student may answer in Bangla or English. Orals are audio-recorded for moderation and appeals; female students' orals follow the university's arrangements for female sections.
  • Load: about 300 orals of 5 minutes is about 25 examiner-hours, a half-day each for 8–10 teachers, held on semester-4 teaching days so students make no extra journey.
  • Recorded variant, where labs have headsets: in the last 10 minutes of the sitting the student records a 3-minute screen-and-voice walkthrough (no camera) of one answer chosen by the harness; examiners review the recordings and call in anyone whose recording does not confirm.

Sittings, retakes and remedial clinics

  • Sitting 1 is in week 10, the earliest week by which CSE-2423 Database Systems has covered the SQL scope; the coordinator confirms that coverage with its instructors each semester. Sitting 2 is in week 14, before final examinations. Results come within five working days, by station, with the error categories recorded by markers.
  • Passed stations are banked until the student passes overall; at a later sitting the student re-sits only the failed stations.
  • A student who has not passed after Sitting 2 receives a fail grade for the semester and re-registers in the next semester, where both sittings are open again alongside the new cohort. Absence counts as not passing that sitting; with documented illness or bereavement the sitting is not counted. There is no cap on attempts, which gives six sittings before semester 7; a student who has not passed by the end of semester 5 meets the adviser for a written study plan.
  • Clinics run in weeks 11–13: for each station, two 2-hour sessions a week (12 hours per station), on semester-4 teaching days around classes. Instructors of the feeder courses run them on rotation, counted in teaching load, helped by teaching assistants or paid senior-student tutors from the strong 15%, who have no access to the question bank. Content: the student's own station feedback, worked examples on the failing error categories, retired tasks under time, and a timed mock station in the last session. Attendance at four of the six sessions for a failed station is required to re-sit it. Retakers planning to sit Sitting 1 get a shorter block in weeks 7–9.
  • A practice contest of retired tasks is open on the department's judge all semester, from home.

Question bank and security

  • Owned by a CCA coordinator (a senior teacher with a load allowance) and a committee with one member from each feeder course: Programming I and II, Data Structures, Object-Oriented Programming & Design, the Developer Tools lab and CSE-2423 Database Systems.
  • Each station holds at least eight task families. Each family has at least four variants testing the same skill at the same difficulty with a different story, data, names and defect positions, in Python, C++ and Java where the station uses a language. Hidden test data are regenerated for every sitting.
  • Every session in a sitting uses a different variant, so the morning session cannot leak the afternoon's. A family is not reused within four sittings; after its third use it is retired to the public practice set, which shows students the format without exposing live tasks.
  • Each committee member adds one new family per semester. Two other teachers solve it blind; it enters the bank only if both finish within 60% of the station time and the statement passes a plain-English review.
  • The bank is kept in a private Git repository on a department server with access logging. Tasks are copied to the exam server on the morning of the sitting; nothing is printed.
  • After each sitting, pass rates are compared across variants; a variant more than 15 percentage points from its station's average is reviewed before reuse. A confirmed leak retires the family, and the affected session's results for that station are reviewed.

Running it for 300 students

  • Seats and days. Plan for up to 330 candidates (one intake plus retakers). At an assumed 30 exam seats per lab with spacing (to be confirmed room by room), six labs running two sessions (09:00–12:30 and 13:30–17:00) give 360 seats in one day, leaving 14 of the department's 20 labs for normal classes. A second day holds overflow, make-ups and accommodation rooms. The sitting day is the weekday on which semester 4 has no classes, with the six labs reserved in the timetable for weeks 10 and 14.
  • Assignment. Sessions are allocated by section; male and female sections sit in separate labs, female sections with female invigilators. Random seat plan, ID check at the door, phones and watches deposited at the front.
  • Invigilation. Two per lab (a teacher and a lab technician), a roaming technical lead per floor and the coordinator at the exam server: 12 lab-sessions a day need 24 invigilator slots.
  • Lock-down. Technicians prepare a separate exam account or boot image the day before and check every machine against a checklist. The lab network reaches only the exam server; Wi-Fi is off; USB storage is blocked; no AI extensions or local model runtimes are installed. The image holds Python 3, g++, OpenJDK, Bash, Git, gdb, the database system used in CSE-2423 Database Systems (SQLite or PostgreSQL), plain editors (Geany, or VS Code with no extensions) and the offline documentation.
  • Marking harness. The department's judge, or DOMjudge, runs on the exam server inside the lab network: it compiles and runs submissions per language against hidden tests and time limits, autosaves and time-stamps every submission, and exports results by station. SQL is marked by result-set comparison, station 5 by the check script. JPlag is run over all code submissions of a sitting; flagged pairs are taken into the oral.
  • Failures. Each lab keeps two spare machines, and a student moved after a fault gets the lost time back. A lab-wide power or network failure voids that session for that lab; its students sit on the reserve day.

Accommodations

  • Approved through the university's student-welfare or disability process before registration for the sitting closes.
  • Extra time (normally a quarter more per station) for a documented disability or learning difficulty, in a small separate room on the reserve day; the oral may be extended too.
  • Screen reader, large-font or high-contrast display, or an adapted keyboard on a prepared machine.
  • An injury that prevents typing: deferral to the next sitting without the sitting being counted.
  • During Ramadan, sessions are timed to end well before iftar.

Feedback to the earlier courses

  • Within two weeks of each sitting the coordinator reports pass rates by station, task family and language; the most frequent error categories (unhandled empty input, off-by-one bounds, wrong structure chosen, missing outer join, unresolved merge conflict, unable to trace a loop); and results grouped by the section in which students took each feeder course.
  • The report goes to the instructors of CSE-1121, CSE-1221, CSE-1130, CSE-2321, CSE-2325, CSE-2423 Database Systems and CSE-2421, and to the programme's outcome-assessment committee.
  • Each feeder course records in its next course file one change made in response, such as a new lab exercise, a supervised test item or more tracing practice. Section-level figures are for course improvement, not by themselves for appraising individual teachers.
  • The results are the programme's direct mid-point evidence for PO1, PO2, PO3 and PO5, and the first-sitting pass rate is the department's measure of whether the middle 60% is reaching the floor.

Notes for the coordinator

In the planned public view this section is shown to the committee only (specification 3.4).

  • Feeder labs should use the same harness for their supervised practical tests, with at least one station-shaped task in semester 3, so no student meets the format for the first time here.
  • This sitting is the "by hand" end of the programme's rule: from semester 4, projects allow AI at Level 2, and CSE-2440 is where the department knows each student can still do the work without it.
  • Keep tasks at floor level. If strong students pass a station easily but the overall pass rate on it is very low, check the wording and English load before concluding that the teaching failed.

About this group of courses: Programming and Algorithms

These seven packages form the programming spine of semesters 1 to 4. Programming I (Python) builds the habits of tracing, decomposing, testing and debugging, and the Developer Tools & Technical Communication Lab supplies the shell, Git, editor and writing skills that every later lab assumes. Programming II (C) adds the memory model; Data Structures (C++) and Object-Oriented Programming & Design (Java) build on it in semester 3, and Algorithms in semester 4 turns structures into design techniques. The Core Competency Assessment then checks, unaided, the floor these courses are meant to produce, before students move on to the track courses and the capstone. while permitted AI use rises from Level 0 in semester 1 to Level 2 in later projects and stays at Level 0 in every test, viva and examination.
