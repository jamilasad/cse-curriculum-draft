Rationale and what changed

In the semester-4 studio students built a web application with little help from frameworks, so they know what routing, data access and session handling are. This course is the "then with tools" half: an industrial stack with static types on both sides of the API, and AI assistance at Level 2 from week 3. Because the tools now produce working screens and endpoints quickly, the course is marked on what they do not guarantee: correct access control, consistent data, behaviour on a bad network, accessibility and measured performance. One stack is fixed per section so that teaching and practical tests are possible: TypeScript and React on the web, Java and Spring Boot with PostgreSQL on the server, and React Native with Expo for mobile. A department that prefers C# with ASP.NET Core on the server can use it without changing the weekly plan. The course has no direct predecessor: the 2022 web courses were folded into the two studios. Left out: native Android and iOS development, visual design as a subject, and any survey of alternative frameworks.

Minimum competency

Every passing student can, unaided:

  • From a given API contract, build a React and TypeScript screen that lists, creates and edits a resource, with loading, empty and error states and no use of any.
  • Add an endpoint to an existing Spring Boot service: controller, validation, service, repository and migration, with correct status codes and one test.
  • Protect an endpoint so that users can read and change only their own records, and prove it with a request that is refused.
  • Say where their application keeps the session or token, how it is sent, when it expires, and what an attacker gains by stealing it.
  • Run an automated accessibility check and a keyboard-only walk-through of a page, and fix the label, contrast and focus problems found.

Stretch goals

  • An offline-first mobile client with a local store, background sync and a stated rule for conflicts.
  • Server-side rendering of one public page with Next.js, with the change in Largest Contentful Paint measured.
  • An Android build produced and distributed by the CI pipeline, with the client's types generated from the OpenAPI contract at build time.

4Back end I with Spring Boot: dependency injection and what the framework now does that students did by hand; controllers, request validation, DTOs against entities, exception handling and one error format; configuration and profiles; OpenAPI generated from code2
5Back end II, persistence: mapping with JPA; lazy loading and the N+1 problem; transactions and isolation in practice; lost updates and optimistic locking; schema migrations; when to write SQL directly2
6Authentication: server sessions against tokens; cookie attributes (HttpOnly, Secure, SameSite); JSON Web Tokens: structure, verification, expiry, the revocation problem; OAuth 2.0 and OpenID Connect authorisation-code flow with PKCE; using an identity provider instead of writing one3
7Authorisation: roles, permissions, ownership and tenant checks enforced on the server at method and query level; broken access control as the commonest serious flaw; CSRF, CORS and cross-site scripting in a single-page application; secrets and configuration3
8Real-time and background work: polling, Server-Sent Events, WebSockets and what each costs; background jobs and schedules; file upload and object storage; client retries and idempotency4
9Mobile I: cross-platform approaches compared (React Native, Flutter, progressive web application) and when native code is needed; React Native with Expo: components, layout, navigation, platform differences; sharing types and the data layer with the web client5
10Mobile II: device storage and secure storage of tokens; offline reads, queued writes and sync conflicts; push notifications; permissions; application lifecycle; building and distributing an Android build; store requirements in outline5
11Accessibility: who is excluded and how; semantic HTML, labels, keyboard operation, focus management, contrast, ARIA and when not to use it; WCAG 2.2 level AA as the working target, and WCAG conformance as a legal and contract requirement in United States and European client work; mobile accessibility; Bangla and English text, dates, numbers and currency6
12Front-end performance: how the browser loads and renders a page; Core Web Vitals (LCP, INP, CLS); bundle size and code splitting; images; caching and content delivery networks; client-side, server-side and static rendering and where Next.js fits; low-end Android phones and slow networks as the design case6
13Back-end performance and production readiness: indexes and query plans (uses CSE-2423), pagination, caching, connection pools, rate limiting; structured logs, health checks, API versioning; packaging for deployment (uses CSE-3654)2, 6
14Reviewing AI-generated application code: typical defects (missing access checks, invented or outdated library calls, inaccessible markup, unbounded queries), dependency and licence hygiene, keeping the architecture intact. Review clinic on a complete sample application; revision6

Weekly plan — lab

CSE-4772 Full-Stack & Mobile Application Engineering Lab · Lab · 1 credits · 2 contact hours a week

Weeks 1–6 are individual guided labs that grow one small application slice by slice; the team project runs from week 6 to week 14. By hand first: in weeks 1–2 types, fetching and state are written without AI-written code or a data library; from week 3 libraries and AI at Level 2 take over. Lab PCs are short of memory for an Android emulator beside an IDE and containers, so mobile labs run on students' own Android phones through Expo Go.

Assessment

Theory. Written mid-term and final, 80 marks. Question types:

  • Read a printed React component and say what is rendered after a sequence of events, or find the defect (stale state in an effect, a missing key, state held in the wrong component).
  • Given TypeScript types and code, say what the compiler rejects and why; write the type for an API response that can succeed or fail in three ways.
  • Given a controller, service and repository listing, find the missing ownership check, the N+1 query or the transaction error, and correct it.
  • Case: session cookies or tokens for a given product, with reasons; or draw the OpenID Connect code flow and say what each party learns at each step.
  • Case: design the sync behaviour of a mobile client for field workers with intermittent connectivity.
  • Given a page-load waterfall and audit summary, diagnose and rank the fixes; given HTML, list the accessibility failures.
  • Recall, at most a fifth of the marks: cookie attributes, the Core Web Vitals, HTTP status codes.

Continuous assessment (20): three Level 0 code-reading quizzes (10); one individual assignment (10), a written review of a supplied AI-generated full-stack pull request containing planted defects.

Lab (100). Weekly lab work and record 30. Practical tests in weeks 7 and 13, 15 each. Project 25: teams of three build a product with a web client, an API and a mobile client for a real or realistic need (a clinic queue, a coaching-centre manager, delivery tracking for a small shop, field data collection for an NGO). Required: at least two roles with ownership rules; OpenID Connect sign-in; one real-time feature; a mobile client that can at least read while offline; core flows passing the accessibility checks; a stated performance budget that is met; migrations; a pipeline running lint, type check and tests; an AI-usage log. Each member owns one slice from screen to table. Viva 15: the student makes a small change to their own slice, live and at Level 0, and explains it. A student who cannot explain their own work does not pass the lab.

Resources

  • Boris Cherny, Programming TypeScript. Dan Vanderkam, Effective TypeScript.
  • Craig Walls, Spring in Action. Laurențiu Spilcă, Spring Security in Action. (If C# is used: Andrew Lock, ASP.NET Core in Action.)
  • Ilya Grigorik, High Performance Browser Networking.
  • W3C, Web Content Accessibility Guidelines (WCAG) 2.2. OWASP Top 10 and the OWASP Cheat Sheet Series.
  • Official documentation for TypeScript, React, Spring Boot, Spring Security, React Native and Expo; MDN Web Docs. These are the working references; the books give the concepts.
  • Tools: Node.js, TypeScript, React, Vite, TanStack Query, React Router, Zod, ESLint, Prettier; a current long-term-support JDK, Spring Boot, Spring Data JPA, Flyway, PostgreSQL; Keycloak; Docker; Expo and Expo Go; Lighthouse and the axe DevTools browser extension; NVDA and TalkBack screen readers; Visual Studio Code or IntelliJ IDEA Community Edition.
  • Hardware: none beyond the computer lab. Three or four low-cost Android phones kept in the lab for students without one.

Notes for the instructor

In the planned public view this section is shown to the committee only (specification 3.4).

  • Students and assistants both produce the working path and stop. Mark the unhappy paths explicitly: refused requests, error states, two users editing at once, no network. Practical test 2 is built from planted defects for this reason.
  • The stack is broad and weaker students drown in tooling. Fix one stack, give a starter repository that builds offline on lab machines (mirror the npm and Maven dependencies), keep weeks 1–6 individual with a check-off each week, and treat the minimum competencies as the floor to rehearse.
  • At Level 2 the volume of code is no evidence of learning. Raise the scope of the project instead of banning the tools, require the usage log, and rely on the live change in the viva.
  • Frameworks change every year; the concepts do not. Teach state ownership, the contract, access control, caching and measurement as the lasting content, and review library versions before each delivery.
