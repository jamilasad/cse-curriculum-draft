Rationale and what changed

CSE-3653 and CSE-3654 gave every student the service models, containers, orchestration basics, a first plan–apply–destroy with infrastructure as code, a delivery pipeline and observability. This course goes one layer down and one step further: how a hypervisor shares a machine, how storage and networks are built beneath virtual machines, and how an infrastructure engineer designs, codes, backs up, prices and migrates a deployment that survives the loss of a host or an availability zone. That is daily work in banks, telecom operators and data-centre providers that run their own virtualised estates, and in exporters that run clients' cloud accounts; the 2022 syllabus had no counterpart. By hand first: students write a virtual machine definition, plan address ranges and read plan output themselves before they use templates, modules and AI assistants. Left out: containers, Kubernetes and pipelines (reused from CSE-3654, not retaught), serverless application development, building an OpenStack cloud, and console click-through training. SWE and SEC students taking it as a substitution get a self-paced Linux primer in week 1 instead of relying on CSE-3677.

Minimum competency

Every passing student can, unaided:

  1. Create a virtual machine from a cloud-init template on KVM or Proxmox VE, attach it to a given VLAN, and log in with an SSH key.
  2. For a stated requirement, draw a virtual private cloud across two availability zones with public and private subnets, non-overlapping address ranges, route tables and security groups, and trace a request from the internet to the database.
  3. Read a Terraform or OpenTofu module and its plan output, say what will be created, changed or destroyed, and correct one error.
  4. Restore a virtual machine or a database from backup and state the recovery point and recovery time actually achieved.
  5. Estimate the monthly cost of a small deployment and name its two largest cost items.

Stretch goals

  • Build a three-node Ceph cluster in nested virtual machines, fail one disk and then one node, and explain what the cluster did.
  • Build server images with Packer in a pipeline so that servers are replaced, never patched in place.
  • Add a second region with DNS failover, measure the real recovery time, and sit the AWS Solutions Architect Associate examination.

Weekly plan — lab

CSE-4788 Cloud Infrastructure & Virtualization Lab · Lab · 1 credits · 2 contact hours a week

Lab environment, cost control and access:

  • Local first. The department's Proxmox VE cluster (four to six hosts with hardware virtualisation; reused desktops with 32 GB of memory will do) gives each pair a nested project they can build and break. Weeks 1–6, backup and migration run there at no running cost. A single lab PC with KVM and libvirt is the fallback.
  • Public cloud in short sessions. Weeks 7–11 and the project use sandbox accounts paid and owned by the department: member accounts in a department AWS organisation, each with a fixed budget, supplemented by AWS Academy Learner Lab accounts if the university joins AWS Academy. Check each year which services each sandbox permits; identity exercises need full identity management. No student needs a payment card or a personal cloud account, and no assessed task depends on one.
  • Cost controls, set before the first resource: a budget alert per account at a low threshold; guardrail policies limiting regions and instance sizes; a mandatory owner tag; an Infracost estimate with every plan; destroy at the end of each session, plus a scheduled teardown job that deletes anything untagged or older than a day. NAT gateways, load balancers and managed databases are created only in the week they are studied, for under two hours.
  • The Proxmox web console needs only a browser; the lab room is open outside class for students without a capable laptop.

Assessment

Theory. Mid-term and final (80). At least half the marks are application and analysis; recall is at most a fifth. Typical questions:

  • fio and iperf3 results for emulated and virtio devices: explain the difference and recommend a configuration.
  • Five services with expected growth: write an address plan across two zones, and find the overlap and the missing route in a given plan.
  • A deployment diagram: list the single points of failure, compute availability, and redesign it to meet a stated target at least cost.
  • A Terraform plan output: say what will be replaced and which change will cause an outage, and how to avoid it.
  • A service with recovery objectives and a budget: choose a recovery strategy and justify it.
  • A monthly bill broken down by service: find three savings and estimate each.

Continuous assessment (20): Level 0 quizzes, best three of four (10); two assignments (10): a written design review of a supplied architecture, and a three-year cost comparison of owned servers against cloud for a stated Bangladeshi organisation.

Lab (100). Weekly lab work and lab record 30; two supervised practical tests at Level 0, 30; lab project 25; individual viva 15. Project (teams of two or three): a resilient deployment of a supplied web application or the team's capstone product, with the primary in one failure domain and a recovery copy in another (a second zone or region in the sandbox, or the local Proxmox cluster), all defined as code. Deliverables: architecture note, cost estimate, tested failover and failback, backup-and-restore runbook, and a migration plan for the primary. A student who cannot explain every resource in the team's plan does not pass the lab.

  • Software (all free): Proxmox VE, Proxmox Backup Server, KVM and QEMU, libvirt (virsh, virt-install, virt-manager), virt-v2v, qemu-img, Open vSwitch, ZFS, Ceph (demonstration), cloud-init, Packer, Terraform or OpenTofu, TFLint, Checkov, Infracost, restic, fio, iperf3, tcpdump, AWS CLI.
  • Hardware: the Proxmox cluster above and a managed switch with VLAN support.

Notes for the instructor

In the planned public view this section is shown to the committee only (specification 3.4).

  • The commonest real failure is a forgotten resource and a bill. Make teardown a graded habit from week 7 and look at the budget dashboard every week.
  • Weaker students struggle most with address planning. Give a subnetting worksheet, drill it in weeks 6–8, and require a diagram before any code. Pair SWE and SEC substitution students with INF students for the first three labs.
  • Test the cluster and the nested templates before the semester and keep a known-good template; a broken host costs a whole lab session.
  • AI assistants write Terraform and libvirt XML quickly, but they invent arguments, use outdated syntax, open security groups to the whole internet, and add NAT gateways and large instances without mentioning cost. Every AI-drafted file goes through validate, plan, the static checks and an Infracost estimate, and is applied in the sandbox before anywhere else; the lab record keeps the plan, and the student explains each resource in it. The Level 0 tests and viva check that the student can read a plan and write a small module unaided.
