Rationale and what changed

Data Structures taught students to build and use structures; this course teaches them to design an algorithm for a problem they have not seen before, argue that it is correct and predict its cost. It takes the place of the algorithms theory and lab courses of the 2022 syllabus and absorbs Competitive Programming 1 and 2: the weekly judged problem sets begun in CSE-2322 continue in CSE-2422, and contest training stays as a co-curricular activity. An AI assistant now produces any textbook algorithm, its code and its proof on request, so the weight moves from reproducing algorithms to the steps the assistant cannot take for the student: turning a loosely stated problem into a precise model, choosing among approaches with reasons, arguing correctness, and checking a proposed solution with counterexamples and brute-force testing. NP-completeness is introduced informally and through reductions; the formal treatment (Turing machines, the Cook–Levin theorem) is left to CSE-4751. Left out on purpose: range-query structures beyond what the problem sets need, computational geometry, linear programming, and the theory of approximation and randomised algorithms.

Minimum competency

Every passing student can do the following on paper or on a lab machine with no AI tool, no internet and no notes:

  • State the Θ running time of a given loop nest or recursive function with a one-line reason, and solve a divide-and-conquer recurrence with the master theorem or a recursion tree.
  • Hand-run Dijkstra's algorithm, Kruskal's algorithm with union–find, a topological sort and a DP table (knapsack, LCS or edit distance) on a small given input, and write the resulting table, order or tree.
  • Given a proposed greedy rule for a scheduling or selection problem with at most six items, give a counterexample or explain why none exists.
  • Recognise which standard technique (sorting with a sweep, BFS, Dijkstra, one- or two-dimensional DP) solves a problem stated in words, and get an accepted C++ solution on the judge within 45 minutes.
  • Write a brute-force solution and a stress test that compares it with a faster solution on random small inputs, and use it to locate a planted bug.

Stretch goals

  • Write full proofs: optimality of Huffman coding, correctness of Dijkstra's algorithm, an NP-completeness reduction from 3-SAT.
  • Use maximum flow beyond matching: edge-disjoint paths, project selection by minimum cut.
  • Solve the challenge problems in every set and take part in the programming club's ICPC-style contests.

Weekly plan — theory

Each technique is taught in the order model, design, argue, analyse; the textbook algorithm is the worked example, not the goal. The mid-term covers weeks 1–7.

Weekly plan — lab

CSE-2422 Algorithms Lab · Lab · 1 credits · 2 contact hours a week

Each two-hour session has a 15-minute hand-simulation warm-up on paper, a judged set of three core, two standard and one or two challenge problems, and a bench check-off in which the student explains one accepted solution chosen at random. The sets keep the format and judge accounts of CSE-2322. Each algorithm is written by hand once; after that the library version (std::sort, std::priority_queue, std::string::find) is used.

Assessment

Theory. The written mid-term and final (80) are made of:

  • Model and design (about 25%): a problem in a setting (bus routes between upazilas, exam-hall allocation, scheduling jobs on a printer) to be modelled, solved in pseudocode or any language, and costed. A correct brute force with its cost earns part of the marks; syntax is not marked.
  • Prove or refute (about 15%): prove a proposed greedy choice with an exchange argument or give a counterexample; find the flaw in a proposed algorithm, often presented as an assistant's answer, and give an input on which it fails.
  • Trace (about 20%): fill in a DP table and recover the solution; run Dijkstra, Kruskal with the union–find state, a topological sort or the KMP prefix function on a small input.
  • Analyse and choose (about 15%): the cost of given code or a recurrence; the amortised cost of a sequence of operations; which approach fits given limits and weights, with reasons.
  • Reductions and hardness (about 10%, final only): reduce a problem to shortest paths or flow; explain why a problem is NP-hard and what to do about it in practice.
  • Recall (about 15%): definitions, statements of theorems, properties of named algorithms.

Continuous assessment (20): ten-minute paper quizzes at Level 0 in most weeks (trace a table, solve a recurrence, find a counterexample), best eight counted (10); three written assignments at Level 1, each with one modelling problem and one correctness argument (10), where the mark is given only after the student explains or adapts one randomly chosen answer in class.

Notes for the instructor

In the planned public view this section is shown to the committee only (specification 3.4).

  • The usual failures are coding before modelling, trusting a greedy rule because it passed the samples, a DP whose state was never written in words, and Dijkstra on negative edges. Every problem in class and lab starts on paper with the modelling card, every DP starts with one sentence saying what a table entry means, and every greedy week includes a counterexample hunt.
  • Support for the weaker majority: the week-1 diagnostic sends students who lack the Data Structures basics to a refresher worksheet and a weekly support hour run by the lab instructors with senior student mentors from the programming club; two missed core sets or two failed quizzes bring a call to the same hour. Each judged problem has an easy version with small limits that a brute force passes, so every student has a working, tested baseline before optimising. Proofs are first taught with fill-in-the-blank exchange-argument and invariant templates, then on a blank page. Both practical tests open with a minimum-competency problem. No mark depends on English grammar; at the bench and in the viva a student may explain in Bangla, with the technical terms in English.
  • An assistant writes Dijkstra or LCS and a convincing proof in seconds, and is often wrong on a slightly changed problem. Use this in class: show an assistant's answer to a modified problem and have students break it with a stress test or a counterexample. Set problems in local settings with altered details so they do not match a textbook problem, and give the marks to the model and the argument. Weekly marks are small and tied to bench explanation; do not rely on AI-detection tools. The Level 2 project is where students practise supervising assistant output, and the log and viva check that they did.
  • Keep the judge, set format and stress-test kit consistent with CSE-2322. The practical tests rehearse the "choose and use a data structure" part of CSE-2440 in the same semester. NP-completeness stays informal here because CSE-4751 treats it formally; dynamic programming and graph search are used again in the AI & Data track.

About this group of courses: Programming and Algorithms

These seven packages form the programming spine of semesters 1 to 4. Programming I (Python) builds the habits of tracing, decomposing, testing and debugging, and the Developer Tools & Technical Communication Lab supplies the shell, Git, editor and writing skills that every later lab assumes. Programming II (C) adds the memory model; Data Structures (C++) and Object-Oriented Programming & Design (Java) build on it in semester 3, and Algorithms in semester 4 turns structures into design techniques. The Core Competency Assessment then checks, unaided, the floor these courses are meant to produce, before students move on to the track courses and the capstone. while permitted AI use rises from Level 0 in semester 1 to Level 2 in later projects and stays at Level 0 in every test, viva and examination.
