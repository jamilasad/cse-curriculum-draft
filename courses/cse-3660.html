Rationale and what changed

Every graduate will be expected to build with language models and to work alongside coding agents, whichever track they choose. In this studio each student ships a deployed product with an AI feature, built with an AI-assisted workflow; with CSE-2434 it replaces the four small development courses of the 2022 syllabus. The course is vendor-neutral. Model providers, agent tools and prices change every year, so the outline fixes the skills (specification, structured output, tool use, retrieval, evaluation, cost control, guardrails, review of generated code) and leaves the products to be chosen before each offering. Left out: training and fine-tuning models (AI & Data track) and the mathematics of transformers (CSE-3545 covers them at concept level). By hand first: each student writes a raw API call and a schema-validated extraction unaided before any agent writes code for the team. With tools afterwards: coding agents do much of the typing, and the student's work becomes specifying, testing, reviewing and deciding.

Minimum competency

  • Write, without an assistant, a short program that sends a prompt to a model API, asks for JSON matching a given schema, validates the reply and handles a failed call.
  • Trace one user request through their own product: what is retrieved, what is sent to the model, which tools can be called, and what is checked before the answer is shown.
  • Build a test set of at least 20 cases for a given feature and report the pass rate before and after a change.
  • Estimate the cost of 1,000 requests from token counts and a price table.
  • Show a prompt-injection attempt against their own feature and say which control stops it or limits the damage.

Stretch goals

  • Serve an open-weight model locally and compare it with a hosted model on the team's test set for quality, latency and cost.
  • Build a long-running workflow with saved state, human approval steps and trace-based debugging, and show it recovering from a failed step.
  • Release the team's evaluation harness as an open-source repository with documentation that another team can follow.

Weekly plan — studio

Each three-hour session has a short taught segment followed by team work. Teams have three or four members. Products serve a real user group where possible (a department office, a local shop, a student society). Bangla-language input is allowed and must then be covered by the test set.

Assessment

There is no written examination. The studio scheme from the framework applies.

ComponentMarksEvidence
Team product against milestones40Four milestones of 10 marks (weeks 3, 7, 10, 13); no milestone is marked without a test-set score
Individual contribution20Commits and reviews, the two individual exercises, usage log, agent-failure analysis, tool-trial note
Individual viva20Week 14, Level 0, with a short live task
Documentation and demonstration20README, architecture, evaluation, cost and safety reports; demonstration in English

Every product must:

  • be deployed and reachable by its users, and still work in reduced form when the model API is unavailable;
  • have at least one AI feature with schema-validated output and either tool use or retrieval;
  • carry a test set of at least 50 cases by Milestone 4, with graders that run from one command;
  • state its cost and latency per request, and have guardrails that another team has tested.

A student who cannot explain their own committed work in the viva does not pass the studio, whatever the team's mark.

Resources

  • Books: Huyen, AI Engineering; Alammar and Grootendorst, Hands-On Large Language Models.
  • References: the OWASP Top 10 for LLM Applications; the NIST AI Risk Management Framework; the current documentation of whichever model APIs are used that year.
  • Software (examples only, reviewed before every offering): a hosted model API with a free or low-cost tier; a small open-weight model served locally with Ollama or llama.cpp; a vector store such as pgvector, Chroma or FAISS; Python or TypeScript; one coding agent or AI-assisted editor that every student can use at no cost; Git hosting with CI.
  • Hardware: ordinary lab computers. A shared department machine with a GPU helps with local models but is not required.

Notes for the instructor

In the planned public view this section is shown to the committee only (specification 3.4).

  • Tools change every year. Before each offering choose that year's API, local model and coding agent and rewrite the examples; do not rewrite the outcomes. Teach no vendor's features as course content, and where two providers are available let teams compare them on their own test sets.
  • Common failures: a demonstration that works on three examples, and an agent where one well-specified call would do. No milestone is marked without a test-set score, Milestone 4 includes cases the team has not seen, and each team must justify every step beyond a single call.
  • Weaker students: Level 3 makes it possible to ship without understanding. The two unaided exercises and the live task in the viva are the check. Supply a reference skeleton, and let weaker students lead on test sets and grading, which reward careful reading more than coding speed.
  • Cost and data: give each team a small fixed API budget, or keep to free tiers and local models, and mark cost control. No personal or confidential data goes to a hosted API; use public or synthetic data. A key committed to a repository is revoked the same day.

About this group of courses: Software, Data, AI and Security Core

These six packages run from semester 4 to semester 6 and carry the part of the core in which students build, secure, deploy and extend real software. Database Systems and the Software Engineering package share semester 4: the database course teaches SQL early enough for the studio to use it, and the web application built in the studio becomes an object that later courses return to. Artificial Intelligence & Machine Learning (semester 5) gives the foundations and the habit of honest evaluation that the AI Application & Agent Engineering Studio (semester 6) turns into a shipped product. In semester 6, Information Security attacks and hardens the semester-4 application and Distributed Systems & Cloud Computing containerises, deploys and monitors it, so each student meets the same piece of software as its builder, its attacker and its operator.
