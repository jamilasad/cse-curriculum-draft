Rationale and what changed

A connected product is a system: sensor, firmware, radio, protocol, back end, data and security, and it fails at the joins. Students have met the parts in separate core courses (microcontrollers, networks, cloud, machine learning); this course has them build the whole path once and measure it. It adds inference on the device, which is the part of AI that embedded employers ask for and that the AID courses do not teach, so it is also the natural substitution for AID students. It is new with the track; it needs only core prerequisites, and it uses the cloud and deployment skills of CSE-3653/3654 for the back end. Left out: radio-frequency and antenna design, circuit-board design, cellular modem internals, writing protocol stacks, training large models, and mobile app development (a generic Bluetooth app and a web dashboard are used instead).

Minimum competency

Every passing student can, unaided:

  • Read a sensor over I2C or SPI and publish the readings as JSON to an MQTT broker over Wi-Fi, with reconnection; subscribe to a command topic and act on it.
  • Draw the path from device to dashboard for a given product and name, for each hop, the protocol and what happens when that hop fails.
  • Connect a device to a broker over TLS with the server certificate checked, and say where each secret is stored.
  • Store device messages in a time-series table, chart them on a dashboard and set one alert rule.
  • Convert a trained small model to 8-bit integers, run it on the microcontroller, and report its accuracy, flash and RAM use and inference time.

Stretch goals

  • LoRaWAN end to end with a lab gateway and an open network server (ChirpStack), with airtime and duty-cycle calculations.
  • Keyword spotting or vibration anomaly detection with a model designed to fit a stated memory and latency budget; compare floating-point, 8-bit and pruned versions on the device.
  • Signed over-the-air update with rollback across three devices, or provisioning of Wi-Fi credentials over Bluetooth Low Energy.

Assessment

Theory. Written mid-term (weeks 1–7) and final (whole course, weighted to weeks 8–14), 80 marks together. Kinds of question:

  • Selection: for a use case with given distances, battery life, data volume and budget, choose the connectivity and defend it with numbers (energy per message, battery-life estimate, airtime).
  • Protocol tracing: given a list of MQTT packets with quality-of-service and retained flags and a disconnection, say what each client receives; design a topic hierarchy for a described fleet.
  • Architecture: draw the device-to-cloud design for a described product, with failure handling at each hop; find the weak points in a given design.
  • Security: threat-model a described device; find the flaws in a provisioning scheme or a code fragment (key in source, certificate check disabled, update not signed).
  • Edge ML: compute a model's memory from its layer sizes and decide whether it fits a given device; read confusion matrices before and after quantisation; choose between cloud and on-device inference for a case.
  • Recall (at most one-fifth of the marks): protocol terms, device classes, definitions.

Continuous assessment, 20: four short in-class quizzes at Level 0 (10); two assignments (10), one a two-page connectivity study with calculations for an assigned local use case, and one a threat model and data-flow diagram of an existing consumer device.

Lab (100). Weekly lab work and lab record 30. Two supervised practical tests 30 (weeks 6 and 12, 15 each; the SDK's offline documentation is available, nothing else). Lab project 25, in teams of two or three: an end-to-end connected product with at least one sensor node, a broker, storage, a dashboard with an alert, a command path, TLS, over-the-air update and one function computed on the device (a model or signal processing). Examples: a vibration monitor for a sewing machine, a pond or water-tank monitor, a cold-room logger, a room energy monitor. Every project reports measured power, latency from event to dashboard and behaviour when the network is lost, and has a README in English, an architecture diagram, a threat model and an AI-use log; the documents are marked with the shared writing rubric. Individual viva 15 on the student's own part and on the whole path.

Resources

  • Textbooks: Perry Lea, IoT and Edge Computing for Architects; Pete Warden and Daniel Situnayake, TinyML; Daniel Situnayake and Jenny Plunkett, AI at the Edge; Kevin Townsend and others, Getting Started with Bluetooth Low Energy.
  • Software, all free: the board's SDK; Eclipse Mosquitto; Node-RED; InfluxDB, or PostgreSQL with the TimescaleDB extension; Grafana; ThingsBoard Community Edition as an optional all-in-one platform; Wireshark; Python with TensorFlow and scikit-learn; TensorFlow Lite for Microcontrollers (now also named LiteRT for Microcontrollers) as the on-device runtime.
  • Industry norm: managed cloud IoT services (for example AWS IoT Core or Azure IoT Hub) and hosted edge-ML platforms such as Edge Impulse. With the open stack students miss managed device registries, fleet provisioning and usage billing; a managed service is demonstrated once by the teacher and its cost model is compared in week 13. A hosted edge-ML platform may be used in the project only after weeks 9–10 have been done by hand.
  • Hardware: a Wi-Fi and Bluetooth microcontroller board per student, sensor kit, current measurement, a few LoRa modules, a lab PC or single-board computer as gateway, an access point on an isolated network.

Notes for the instructor

In the planned public view this section is shown to the committee only (specification 3.4).

  • The usual failure is the demonstration that works only on the bench with a perfect network. Switch off the access point during every demonstration and mark what the device does next.
  • "Sensor to cloud dashboard" copied from a tutorial is the low-effort project. The marks sit in the measurements, the failure handling and the security checklist, which a tutorial does not supply.
  • For weaker students: a fixed reference architecture and a working skeleton for each hop, so that a student who is behind in firmware can still finish the data path. AID students who join by substitution have not taken CSE-4779: pair them with EMB students in weeks 1–5 and give them the task skeleton; in weeks 9–11 the help runs the other way.
  • Assistants write glue code well (MQTT clients, JSON handling, dashboards, small services); allow it and mark what they cannot do. Danger areas: sample code with certificate checking switched off or credentials in the source; blocking network calls inside callbacks that hang the device; library functions and pin numbers that do not exist on this board; PC accuracy reported as device accuracy, or input scaling forgotten after quantisation. Rules: no secret in the repository, certificate checking on, every reported number measured on the device.
