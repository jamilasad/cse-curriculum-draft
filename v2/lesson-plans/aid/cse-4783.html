Minimum competency

Every passing student can, unaided:

  • Given a star schema, write correct SQL with joins at the right grain, GROUP BY, a common table expression and a window function (rank, running total or lag), and check the totals against the source.
  • Given a business question and source tables, draw a star schema and state the grain of the fact table in one sentence.
  • Build a pipeline of at least three dependent steps that can be run twice without duplicating rows, with at least three automated data tests.
  • Read the log of a failed pipeline run and identify the failing step and its cause.
  • Produce a chart that answers a stated question (suitable chart type, labelled axes, a title that states the finding), and mark and mask the personal-data columns of a given table.

2. Class pattern (assumption to confirm)

This follows README assumptions A1–A3.

  • Theory: 3 contact hours a week, given as two 90-minute classes. 14 teaching weeks give 28 classes. Class numbers run 1–28; Classes 2W−1 and 2W are in week W.
  • Lab: one 2-hour session a week, 14 sessions.
  • Examinations: the mid-term (weeks 1–7) is held in an examination week after week 7. The final is held after week 14. Neither uses a class slot. The outline does not say otherwise.
  • Re-split: the department may re-split theory into three 60-minute classes. Use the rule in README A2. The timed blocks below are cut at 10, 20, 30 or 45 minutes so that the split falls between blocks.
  • If the mid-term takes a class slot: it takes Class 14 (week 7). The mid-term review in Class 14 is dropped. Class 14's topics (parametrised runs and backfills, service levels, logs and lineage, continuous integration for pipelines) move into Class 13 as a 20-minute block, and the backfill exercise moves into lab 8, which already builds a scheduled task graph.
  • Quizzes (Level 0, 20 minutes, on paper, mostly SQL): Quiz 1 in Class 5 (week 3), Quiz 2 in Class 10 (week 5), Quiz 3 in Class 17 (week 9), Quiz 4 in Class 25 (week 13). Best three of four count.

The running case

The outline names one running case: a retail chain with shops, an online store and a mobile-payment channel. The instructor-built retail dataset (README A10) models it. It has shops in several districts, an online store, customers, products, orders, order lines, payments (cash, card and mobile payment), returns and stock movements. A generator writes daily order and payment files and an event stream of orders. The generator can plant faults on request: duplicate files, late events, a renamed column, district names spelled two ways (Chattogram and Chittagong), an order paid in two parts. All personal data in it is synthetic, but students treat it as real personal data.

Everything runs on an ordinary lab PC with free software: PostgreSQL and DuckDB as the warehouse, dbt Core as the transformation framework, one orchestrator, a single-node message broker and an open-source dashboard tool. A deliverable without one loses the "checks" point in R1. This follows the outline's instructor note.
  • Marking. Regular sessions (weeks 1–6 and 8–12) are marked with R1 (0–3 each, best 10 of 11). Tests use R2. The viva uses R4 and section 6.6.
  • Repository. Each student (and later each pair) has a Git repository in the course organisation from week 1, with AI-USAGE.md (template T5) and a record/ folder for lab record pages (template T6).

S5. Design: star schema (mid-term 4, 7 marks). A pharmacy chain with 40 branches wants sales by medicine, branch, day and payment method, and wants to see how sales move when a medicine's category is changed by the regulator. Marking notes:

  • Fact table fact_sales_line with additive measures quantity, unit price paid, discount, line amount, cost amount (1).

S6. Analysis: idempotency (mid-term 5, 4 marks). A nightly step runs:

INSERT INTO fact_sales
SELECT * FROM stg_sales WHERE sale_date = CURRENT_DATE - 1;

(a) What happens if it is run twice on the same night? (b) What happens if a failed run is re-run the next morning after midnight? (c) Make it idempotent. Answer: (a) Yesterday's rows are inserted twice; totals double (1). (b) It loads the wrong day: "today minus one" is now a different date, so the failed day is never loaded and another day may be duplicated (1). (c) Pass the run's logical date as a parameter, and delete then insert that date's rows in one transaction, or upsert on the natural key (receipt_no, line_no) (2):

BEGIN;
DELETE FROM fact_sales WHERE sale_date = :run_date;
INSERT INTO fact_sales SELECT * FROM stg_sales WHERE sale_date = :run_date;
COMMIT;

Graded SQL sets in weeks 1–3 (outline).

  • Each set has three levels. Level 1: one table, one aggregate. Level 2: one join at the right grain. Level 3: a CTE or a window function.

Weekly SQL clinic (outline). One hour a week, weeks 1–14, run by the lab instructor or a trained senior student. Weeks 1–7: SQL and schemas. Weeks 8–9: tests and pipeline logs. Weeks 10–12: brief writing and chart checking. Explanations may be in Bangla.

9. Issues for the committee

These are reported, not fixed. Each needs a decision.

  1. Assessment congestion in semester 7 for AID students. The outlines fix CSE-4774 and CSE-4784 practical test 1 in week 7, the same week as the Capstone Project I proposal defence. Both courses hold practical test 2 in week 13, the week of the Capstone I prototype review with individual viva (M3). Both hold project demonstrations and vivas in week 14, with the capstone progress report. AID students therefore face two Level 0 tests and a capstone milestone in each of weeks 7 and 13, and two vivas in week 14. The weeks are set in the outlines, so moving either test is a committee decision.
  2. Lab PC memory and the choice of tools. The outline runs services one at a time, but lab 8 needs ingestion, dbt, an orchestrator and the warehouse working together, and practical test 2 runs a dbt project with the network off. The outline notes that Airflow needs the most memory. The framework does not state the lab PC specification. Before the first offering the department must state the specification and fix the orchestrator (and whether labs 8–9 and test 2 run on DuckDB alone). If a lab PC cannot run the week 8 task graph, the outline's lab 8 cannot be followed as written.
  3. Week 11 is overloaded, and needs an AI tool for every student. Lab 11 holds the governance work (column classification, masking, roles, a row policy), the measurement of AI-written SQL on 15 questions, and the project checkpoint in one 2-hour session. This plan fits them only by moving the checkpoint review out of the session. It also assumes an AI assistant for every student, with no data rows sent to it. The department's AI budget (README track-wide issue 2) does not cover this week. The committee should decide whether to split the week's work or reduce the number of questions, and which AI tool students use.
  4. Week 11 at Level 3 against framework section 6. Framework section 6 sets Level 2 for weekly lab work in semesters 6–8 and lets a course set a stricter level for named weeks, "not a looser one". Level 3 is listed for the AI & Data track, but the framework does not say whether Level 3 counts as looser than Level 2. This plan treats week 11 as Level 3 (AI-written SQL is the material) with coding help under Level 2 conditions, as the track overview says. The committee should confirm this reading, and confirm that it also applies to SWE students taking the course as a substitution.
  5. Thin lab evidence for CLO4 (streams). The outline's lab project does not require a streaming element, so lab CLO4 rests on lab 12 and one viva question: 6 of 100 lab marks (section 6.7). Theory carries 14.5 of 100 marks for CLO4. The committee may accept this, or ask for a streaming element in the project.
  6. SWE substitution in practice. SWE students who take CSE-4783 give up CSE-4781 Software Testing & Quality Engineering. The SWE outline notes that its "Replaces" column assumes same-slot courses are timetabled together; if they are not, the adviser chooses which SWE course is given up. Either way, CSE-4783 must not clash in the timetable with the SWE courses an SWE student keeps, and the class must be planned for a mix of AID and SWE students. Their prerequisites are all core courses, so no other barrier was found.
  7. Who checks the law each year. Week 9 asks for "Bangladesh's own data-protection rules as they stand that year". No one is named to make that check, and CSE-4805, where law is taught, comes a semester later. The committee should name the owner (for example the CSE-4805 teacher, shared with this course).
  8. Preparation work with no allocated time. The instructor-built retail dataset with a generator for daily files, events and planted faults is a substantial build that every lab depends on. Framework section 16 says new courses need training time or adjuncts before first delivery, but no time is allocated for building course datasets.
  9. The shared writing rubric. The outline marks the brief "with the shared writing rubric", which does not exist yet (README track-wide issue 5). This plan uses README R5.
