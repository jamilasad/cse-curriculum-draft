Rationale and what changed

Unit testing was introduced in CSE-2325 and used in the studios as a habit. This course treats testing as engineering: choosing what to test, deriving cases by technique, automating at the right level, and deciding whether software is fit to release. It earns a full course for two reasons. Test automation is a job family in the firms this track serves, and one where careful mid-level students do well. And as assistants write more of the code, the engineer's work moves towards stating what correct means and checking it. It is a new course: the framework's change list shows no testing course in the 2022 syllabus. Left out: formal verification and model checking, heavyweight test documentation, manual test execution as an end in itself, and penetration testing (SEC track).

Minimum competency

Every passing student can, unaided:

  • For a specified function or form with three or four inputs, list the equivalence classes and boundary values and produce a minimal test table with expected results.
  • Write JUnit tests for a given class, including one that uses a test double, which catch a seeded defect.
  • Write one API test and one browser test for a running application that pass on ten consecutive runs.
  • Read a failed pipeline run and say, with evidence, whether the fault is in the product, the test or the environment.
  • Write a defect report (steps, expected and actual result, severity, environment) that a classmate can reproduce without asking a question.

Stretch goals

  • Find a defect with property-based testing (jqwik or fast-check) that the example-based tests missed.
  • Add consumer-driven contract tests between the web client and the API with Pact.
  • Use a model as judge in an evaluation and measure its agreement with human labels; or sit the ISTQB Foundation Level examination.

7End-to-end and user-interface testing: the test pyramid and its critics; browser automation: locators, waiting, page objects; flaky tests: causes, detection, quarantine; mobile testing in outline; automated accessibility checks; what stays manual2, 3
8Static testing: review types from informal to inspection; code review on pull requests: what to look for, how to write a comment, size and turnaround; static analysis: linters, type checkers, bug finders, data-flow analysis; quality gates4
9Testing in the pipeline: stages, fast and slow suites, parallel runs, environments and data, reports; shift left, and testing in production (flags, canaries, synthetic checks; continued in CSE-4881). The test strategy: risk-based priorities, entry and exit criteria, effort estimates3
10Performance testing: load, stress, soak and spike tests; workload models and think time; percentiles, throughput, saturation; reading results to find the bottleneck; performance budgets in the pipeline5
11Security testing basics (uses CSE-3651): static and dynamic scanning, dependency and secret scanning, fuzzing as an idea; testing access control systematically with a role-by-resource matrix; the OWASP Top 10 as a checklist; what is left to specialists5
12Testing AI-generated code: typical defects (plausible but wrong logic, invented library calls and packages, missed edge cases, insecure defaults, tests that assert the defect); a review protocol; generating tests with an assistant and judging them by mutation; property-based and differential checks6

14Managing quality: defect lifecycle, severity and priority; metrics (defect density, escaped defects, coverage, mutation score, flaky-test rate, change failure rate) and how each is gamed; test planning, monitoring and tools; testing careers; revision cases3, 4

Weekly plan — lab

CSE-4782 Software Testing & Quality Engineering Lab · Lab · 1 credits · 2 contact hours a week

Weeks 1–7 use a supplied application with seeded defects, built on the CSE-4771 stack (React, Spring Boot, PostgreSQL). By hand first: in weeks 2–4 test cases are derived on paper and tests are written without AI; from week 5 AI at Level 2 is allowed and its tests are judged by mutation score.

Assessment

Theory. Written mid-term and final, 80 marks. Question types:

  • From a specification, derive equivalence classes, boundary values, a decision table or state-transition cases, and give the smallest set of tests that meets a stated criterion.
  • For 20–30 lines of code, draw the control-flow graph, compute statement and branch coverage of a given test set, add tests to reach full branch coverage, then name a defect that full coverage would still miss.
  • Read a printed test class and find what is wrong with it (no real assertion, shared state, sleeps, mocks of everything, asserting the implementation); rewrite one test.
  • Case: a test strategy for a described system and team (for example a wallet top-up feature, six engineers, fortnightly releases): levels, what to automate, what stays manual, pipeline stages.
  • Interpret evidence: a load-test summary, a coverage and mutation report, or a pipeline log; decide whether to release and justify it.
  • Given an AI-written function with AI-written tests, find the defect the tests miss; design an evaluation set and pass criteria for a described LLM feature.
  • Recall, at most a fifth of the marks: ISTQB definitions and principles.

Continuous assessment (20): three Level 0 quizzes on test design (10); one individual assignment (10), a complete black-box test design for a supplied two-page business specification, with a prioritised test list.

Lab (100). Weekly lab work and record 30. Practical tests in weeks 7 and 13, 15 each. Project 25: individually or in pairs, a test strategy and automated suite for a real application. For students taking CSE-4771 this is their CSE-4772 team product, each student owning named features; others use the supplied application. Required: a one-page risk-based strategy; unit, integration, API and end-to-end tests; a pipeline with a quality gate; a mutation score for one core module; a performance baseline; defect reports for what was found; a one-page quality report ending in a release recommendation with reasons. Marks go to defects found and reasoning, not to the number of tests or the coverage figure. Viva 15: the student explains why chosen tests exist and what defect each would catch. A student who cannot explain their own work does not pass the lab.

  • Vladimir Khorikov, Unit Testing: Principles, Practices, and Patterns.
  • Paul Ammann and Jeff Offutt, Introduction to Software Testing (reference for coverage criteria).
  • ISTQB, Certified Tester Foundation Level Syllabus, version 4.0. OWASP, Web Security Testing Guide.
  • Titus Winters, Tom Manshreck and Hyrum Wright, Software Engineering at Google (chapters on testing and code review). Lisa Crispin and Janet Gregory, Agile Testing.
  • Tools: JUnit 5, AssertJ, Mockito, Testcontainers, REST Assured, JaCoCo, PIT; Vitest and React Testing Library; Playwright; k6; ZAP; ESLint, SpotBugs, Semgrep, SonarQube Community Build; Trivy or OWASP Dependency-Check; the CI service used in CSE-3654. For week 12: a short harness written in the test framework, or promptfoo; a small open-weight model run locally with Ollama where there is no API budget.

Notes for the instructor

In the planned public view this section is shown to the committee only (specification 3.4).

  • Students write tests that pass, not tests that can fail. Use seeded defects and mutation testing throughout so that marks depend on defects caught, and never mark by test count or coverage alone.
  • Test design by technique is procedural and learnable, and gives mid-level students a dependable skill and a job route; tell them so. Drill the tables by hand in weeks 2–4 on specifications written in simple English. Discussion may be in Bangla; defect reports are in English from a template.
  • Assistants generate tests in seconds, and the tests tend to mirror the implementation, defects included. That is why weeks 2–4 are by hand and why, from week 5, any generated test must survive the mutation check or be deleted.
  • The week-12 lab needs either a small API budget or a local model, and its results differ from run to run. Do not hide this; it is the point of the lab.
