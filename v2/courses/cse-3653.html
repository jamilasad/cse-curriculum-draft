Rationale and what changed

This course is new and has no counterpart in the 2022 syllabus. Deployment and cloud are now part of every software job, and the infrastructure and operations roles they create suit mid-level students well. The course joins two things usually taught apart: the ideas that explain why distributed systems fail the way they do, and the practice of packaging, deploying and observing software on rented infrastructure. Left out: proofs (the impossibility result for consensus is stated, not proved), Paxos, Byzantine fault tolerance beyond a mention, big-data processing frameworks (AI & Data track), and console click-through training for any one provider. The lab needs no paid account; it runs on local tools and free tiers. By hand first: students run a service by hand, then write a Dockerfile, a Compose file and a Kubernetes manifest themselves. With tools afterwards: templates, infrastructure-as-code modules and AI assistants, whose output they must run and explain.

Minimum competency

  • Write a Dockerfile for a given web service, run it with a database using Docker Compose, and explain image, container, volume and port mapping.
  • Given an event diagram for three processes, assign Lamport timestamps and say which events are concurrent.
  • For a replicated store during a network partition, say what a client can observe under strong consistency and under eventual consistency.
  • Read a CI pipeline definition, fix a failing stage, and deploy a change through the pipeline.
  • Find the cause of an injected fault using logs and a metrics dashboard.

Stretch goals

  • Implement Raft leader election, or the full replicated log, and test it under injected crashes and message loss.
  • Provision a free-tier cloud environment with Terraform or OpenTofu, load-test the service, and write a capacity and cost note.
  • Sit AWS Certified Cloud Practitioner.

Assessment

Theory (100). Written mid-term and final (80). At least half the marks are application and analysis: assign Lamport or vector timestamps on an event diagram and identify concurrent events; given N, R and W and a failure, say whether a read can be stale; choose a consistency model for a described feature and justify it; explain the bug when a retry policy meets a non-idempotent endpoint, and fix it; sketch an architecture for a case (ticket sales before Eid) and mark its bottlenecks and single points of failure; compute the availability of components in series and in parallel; read a printed Dockerfile, Kubernetes manifest or pipeline file and find the error or predict the behaviour; diagnose a fault from a log extract and a dashboard; estimate a monthly bill from a price table and suggest a saving. Recall is at most a fifth; provider product names are not examined. Continuous assessment (20): Level 0 quizzes (10); two assignments (10), an analysis of a published outage post-mortem and an architecture and cost note for the lab project.

Lab (100). Weekly lab work and lab record 30; two supervised practical tests at Level 0 in weeks 6 and 12, 30; lab project 25; individual viva 15. The project, done in groups of three, is to operate an application the group already has (the CSE-2434 product or the CSE-3660 product): containers, a CI/CD pipeline, deployment on a local cluster or a free-tier host, a dashboard and an alert, a runbook, a cost estimate, and one recorded failure experiment with a short post-mortem. A student who cannot explain their own work in the viva does not pass the lab.

Resources

  • Textbooks: van Steen and Tanenbaum, Distributed Systems; Kleppmann, Designing Data-Intensive Applications; Burns, Beda and Hightower, Kubernetes: Up and Running; Kim, Humble, Debois and Willis, The DevOps Handbook; Beyer, Jones, Petoff and Murphy (eds.), Site Reliability Engineering; Morris, Infrastructure as Code.
  • Software, free for this use: Docker and Docker Compose; minikube or kind; GitHub Actions or GitLab CI; Terraform or OpenTofu; Prometheus and Grafana; RabbitMQ; Redis; etcd; PostgreSQL; Nginx; k6; LocalStack (optional); the AWS Free Tier (optional).
  • Hardware: lab computers with enough memory for Docker and a single-node Kubernetes cluster. A department server used as image registry and deployment target helps.

Notes for the instructor

In the planned public view this section is shown to the committee only (specification 3.4).

  • Set-up and cost are the practical risks. Container images are large, so keep a local registry mirror, pull images before each lab, and hand out a tested reference repository in week 1. No assessed task needs a paid account or a payment card; where cloud accounts are used, set a budget alert first and destroy resources at the end of each session.
  • Common failure: configuration files copied without understanding. The first Dockerfile, Compose file and manifest are written by hand, and the tests ask students to predict behaviour and repair faults, which copying does not prepare them for.
  • Weaker students: the work is concrete and visible, and mid-level students often do well here. Teach the theory through the experiments of weeks 4, 5 and 7 before the formal models, and give step-by-step checklists for the first three labs only.
  • AI: assistants write configuration fluently, including outdated and insecure settings. From week 4 students may use them, but must run what they are given and explain every line in the viva.

About this group of courses: Software, Data, AI and Security Core

These six packages run from semester 4 to semester 6 and carry the part of the core in which students build, secure, deploy and extend real software. Database Systems and the Software Engineering package share semester 4: the database course teaches SQL early enough for the studio to use it, and the web application built in the studio becomes an object that later courses return to. Artificial Intelligence & Machine Learning (semester 5) gives the foundations and the habit of honest evaluation that the AI Application & Agent Engineering Studio (semester 6) turns into a shipped product. In semester 6, Information Security attacks and hardens the semester-4 application and Distributed Systems & Cloud Computing containerises, deploys and monitors it, so each student meets the same piece of software as its builder, its attacker and its operator.
