Rationale and what changed

Operating Systems stays a full core course: every program a graduate writes runs as a process, competes for memory, and reads and writes files, and most of it is now deployed in containers. The course is organised around three ideas (sharing the processor and memory, concurrency, and persistent storage) and then adds virtual machines, containers and the basics of operating-system security, which Distributed Systems & Cloud Computing and the Cloud & DevOps Lab build on in semester 6. The lab is on Linux in C and uses the real system-call interface: processes, a simple shell, threads and locks, and containers. Left out: disk-scheduling variants worked by hand, deadlock-avoidance arithmetic beyond one worked example, kernel development (offered as a stretch goal), and distributed operating systems, which belong to CSE-3653.

Minimum competency

  • Given a short C program that calls fork, exec and wait, draw the process tree and list the possible outputs.
  • Write a C program in which a parent starts a child that runs another program, with the child's output sent to a file or through a pipe.
  • Find the race in a short multithreaded program and fix it with a mutex; explain a given deadlock and remove it by ordering the locks.
  • On paper, schedule up to five jobs under round-robin and compute waiting and turnaround times; translate a virtual address through a given single-level page table.
  • Run a program in a container from a given image, limit its memory, and say what the container isolates and what it shares with the host.

Stretch goals

  • Add a system call to the xv6 teaching kernel and run it under QEMU.
  • Build a container by hand from Linux namespaces and control groups, without Docker.
  • Write a memory allocator (malloc and free) with a free list and measure its fragmentation.

Assessment

Theory. Mid-term (weeks 1–7) and final (whole course, weighted to weeks 8–14) together carry 80 marks. At least half the marks are for application and analysis:

  • read a C program using fork, wait, exec or pipes, draw the process tree and list the possible outputs;
  • decide whether a threaded fragment has a race, give an interleaving that produces a wrong result, and fix it; find the deadlock in a fragment and repair it;
  • draw a schedule and compute the metrics, then argue which policy suits a described workload;
  • translate addresses through a given page table; count page faults for a reference string under two policies; diagnose a described case of thrashing and propose a remedy;
  • say how many blocks are read to open a given path, and what is lost if the machine crashes between two named writes, with and without a journal;
  • choose a virtual machine or a container for a described deployment and justify the choice.

Recall (definitions, lists of conditions, state names) is at most a fifth. Continuous assessment (20): four quizzes of about 15 minutes at Level 0, best three counted (10); two problem sets and one task of reading and explaining a short piece of unfamiliar systems code, at Level 1 (10).

Lab (100). Weekly lab work and lab record 30. Two supervised practical tests on lab machines, Level 0, 30. Lab project 25, alone or in pairs, one of: (a) the shell completed with pipelines of any length, background jobs, built-in commands and signal handling; or (b) a multithreaded job processor, with a thread pool and a bounded queue, that analyses a directory tree of files and runs in a container under a memory limit. Either comes with tests, a design note in English and the AI-use log required at Level 2. Individual viva 15, in which the student makes a small change to their own code. A student who cannot explain their own code in the viva does not pass the lab.

Notes for the instructor

In the planned public view this section is shown to the committee only (specification 3.4).

  • Weak C is the main obstacle: students last used it two semesters earlier. Use the week 1 diagnostic to send those who need it to a two-session clinic on pointers, strings and structs before week 3.
  • Students learn scheduling arithmetic and still cannot say what fork returns, so examine the process interface by reading code. They also believe a concurrent program is correct because it ran once: make them run it thousands of times in a loop and under a sanitizer.
  • Assistants write a toy shell on request. The shell is therefore built in stages with each stage checked at the bench, and both the practical tests and the viva ask for a change to the student's own code. A good review exercise is an assistant-written thread pool with a race for the class to find.
  • Coordinate with CSE-2425 (the hardware side of virtual memory, already taught), with CSE-3543 (sockets, taught in that lab) and with CSE-3654 (containers used at scale in semester 6).

About this group of courses: Systems and Hardware Core

These six packages take the student from a single gate to a networked computer running many programs. Digital Logic Design (S3) builds gates, registers and state machines; Computer Organization & Architecture (S4) assembles those parts into a RISC-V processor with a memory hierarchy and shows how C becomes instructions. Semester 5 then looks at the machine from three sides: Microcontrollers & Embedded Systems programs a bare processor with no operating system, Operating Systems explains the software that shares one machine among many programs, and Computer Networks connects machines to each other. Automata, Languages & Compilers (S7) closes the sequence with what machines can and cannot compute, and how the languages used throughout the programme are translated and run.
