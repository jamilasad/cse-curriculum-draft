Rationale and what changed

Most software written by Bangladeshi exporters, banks and MFS providers is delivered through the web and through APIs, and flaws in that code are a common way in for attackers. Students met the main flaws briefly in the semester-4 studio and at overview level in CSE-3651; this course takes each class to its root cause, exploits it in the lab, fixes it in code and then catches it automatically in the pipeline. It has no counterpart in the 2022 syllabus. Each flaw is exploited by hand with an intercepting proxy before any scanner is used, and code is reviewed by hand before static-analysis tools are run on it. Applications that embed language models are included because every student has just built one in CSE-3660. Left out: binary exploitation and reverse engineering, mobile application internals, and exploit development.

Minimum competency

Every passing student can, unaided:

  1. Capture and modify a request with an intercepting proxy, and demonstrate one injection flaw and one access-control flaw on a lab target.
  2. Given a short vulnerable code fragment (SQL injection, stored cross-site scripting, or a missing authorisation check), identify the flaw and write the fix.
  3. Explain how a cookie or token authenticates a request and name the settings that protect it.
  4. Run a static-analysis tool and a dependency scanner on a repository and say which findings matter and why.
  5. Write one finding in standard form: title, affected component, steps to reproduce, impact, severity, recommended fix.

Stretch goals

  • Chain two or more low-severity findings into one high-impact attack and document the chain.
  • Write a custom Semgrep rule that catches a flaw class in the team's own semester-4 code base, with test cases.
  • Run an automated test set against the lab's language-model application (for example with garak or promptfoo) and compare what it finds with manual testing.

Assessment

Theory. Mid-term and final (80). At least half the marks are application and analysis; recall is at most a fifth. Typical questions:

  • Twenty to thirty lines of code: find the flaw, describe a request that exploits it, write the fix.
  • Request and response pairs: name the vulnerability class and the evidence for it.
  • A case (an MFS agent portal, a multi-tenant school system): design login, session handling and authorisation, and justify each choice.
  • A scanner report with eight findings: decide which are real and rank them.
  • A diagram of an application with a language model, a document store and a tool: mark every path by which injected text can arrive, and place controls.
  • Rewrite a badly written finding so that a developer could act on it.

Continuous assessment (20): four Level 0 quizzes, best three counted (10); two assignments (10), a threat model of the student's own semester-4 studio application and a written code review.

Lab (100). Weekly lab work and lab record 30; two supervised practical tests at Level 0, 30; lab project 25; individual viva 15. Project (teams of two or three): a scoped penetration test of a department-built application the students have not seen, with flaws planted across at least six classes. Deliverables are the signed scope and test plan, a report with a one-page management summary and findings in standard form with severity and evidence, patches for two findings and retest evidence. In the viva each student reproduces one of the team's findings live and explains the fix; a student who cannot does not pass the lab.

Resources

  • Textbooks: Dafydd Stuttard and Marcus Pinto, The Web Application Hacker's Handbook; Andrew Hoffman, Web Application Security; Michal Zalewski, The Tangled Web; Corey Ball, Hacking APIs; Adam Shostack, Threat Modeling: Designing for Security.
  • Free references: OWASP Top 10, Application Security Verification Standard, Web Security Testing Guide, API Security Top 10, Top 10 for LLM Applications and the Cheat Sheet Series.
  • Software (all free): Docker, OWASP Juice Shop, DVWA, OWASP WebGoat, OWASP crAPI, Burp Suite Community Edition, ZAP, sqlmap, ffuf, hashcat, Semgrep, Gitleaks, Trivy, OWASP Dependency-Check; Ollama with a small local model, or the model access arranged for CSE-3660, for the week-13 target.
  • The department builds and maintains two unseen targets: one for the practical tests and one for the project.

Notes for the instructor

In the planned public view this section is shown to the committee only (specification 3.4).

  • The common failures are pressing the scanner button first and following published walkthroughs of the public targets. Use public targets for practice, assess on department-built ones, and mark the explanation and the fix, not the captured flag.
  • Each weekly lab has three steps: exploit with guidance, explain the root cause in two sentences, fix and retest. The guided first step keeps weaker students moving, and the minimum competency asks for only one injection flaw and one access-control flaw, done properly. Start with code in the language of the semester-4 studio.
  • AI assistants write payloads and patches. Their patches often block the example payload and leave the flaw in place, and code they generate often contains the flaws taught here. Use both facts: give students an AI-written patch and an AI-generated endpoint to review. Students log AI use at level 2, and tests and the viva are at Level 0.
  • SWE students taking the course as a substitution have not used the track range. Give them the range guide and the rules of engagement a week early; nothing else from CSE-3675 is assumed.
