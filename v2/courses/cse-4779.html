Rationale and what changed

The core course in semester 5 leaves students able to write bare-metal firmware: one loop, a few interrupts, one peripheral at a time. Products need several activities at once, each with a deadline, in a few kilobytes of memory, for years without a restart. This course teaches how that is done with a real-time kernel, and it applies the scheduling and synchronisation ideas of Operating Systems under hard limits: no memory protection, little memory, and time that matters. It is new with the track and is its central firmware course. Embedded Linux appears at an introductory level only, enough to choose between it and a real-time kernel. Left out: writing a complete kernel, Linux kernel driver development, multi-core real-time scheduling, AUTOSAR, and safety certification beyond knowing that the standards exist.

Minimum competency

Every passing student can, unaided:

  • Create two or three tasks that pass data through a queue, and say what state each task is in at a marked moment.
  • Share data between an interrupt handler and a task correctly (interrupt-safe call, deferred handling, critical section), and point out the race in a supplied faulty example.
  • For three periodic tasks with given periods and execution times, compute the utilisation, assign rate-monotonic priorities and decide by a timeline whether every deadline is met.
  • Use a debugger (breakpoint, watch, call stack) and a logic analyser to measure how long a task or interrupt handler takes.
  • Read one peripheral's section of a datasheet and write a driver function for it with correct register access.

Stretch goals

  • Port the lab project to Zephyr, using its devicetree and driver model, and compare memory footprint and effort.
  • Write a minimal pre-emptive context switcher for the lab processor with two tasks, to see what the kernel does on each tick.
  • Build an embedded Linux image with Buildroot, access a sensor from user space, and measure scheduling latency under load with and without the real-time pre-emption option.

Assessment

Theory. Written mid-term (weeks 1–7) and final (whole course, weighted to weeks 8–14), 80 marks together. Kinds of question:

  • Schedulability: draw the timeline of a task set under rate-monotonic and earliest-deadline-first scheduling; compute a response time; say which task misses under overload.
  • Tracing: given task code with priorities and queue operations, give the order of output and the state of each task at marked points.
  • Find and fix the defect: a blocking call in an interrupt handler, a missing volatile, an unprotected shared variable, two locks taken in opposite orders, priority inversion.
  • Design: divide a described product into tasks, interrupt handlers and queues; assign priorities and justify them; choose polling, interrupt or DMA for each device.
  • Calculation: stack budget, battery life from a duty cycle, latency budget from sensor to actuator.
  • Case: bare metal, real-time kernel or embedded Linux for three products; an update scheme for a device that cannot be reached by hand.
  • Recall (at most one-fifth of the marks): task states, definitions of jitter and latency, watchdog types.

Continuous assessment, 20: four short in-class quizzes at Level 0 (10), on timelines and code tracing; two assignments (10), one schedulability problem set worked by hand and then checked with a small simulation the student writes, and one written design review of a supplied firmware architecture.

Lab (100). Weekly lab work and lab record 30. Two supervised practical tests 30 (weeks 6 and 12, 15 each). Lab project 25, in pairs: a multi-task instrument or controller, for example a low-power data logger with a command shell, a closed-loop motor or temperature controller with a stated control period, or a vibration or sound monitor. Required in every project: a task diagram with justified priorities; a table of every shared resource and its protection; measured worst-case response against a stated deadline; memory and power budgets; a watchdog; a README in English; an AI-use log. Individual viva 15, which always includes "what happens if this interrupt arrives here?" asked on the student's own code.

Resources

  • Textbooks: Richard Barry, Mastering the FreeRTOS Real Time Kernel (free from the FreeRTOS project); Giorgio Buttazzo, Hard Real-Time Computing Systems; Elecia White, Making Embedded Systems; Joseph Yiu, The Definitive Guide to ARM Cortex-M3 and Cortex-M4 Processors (if a Cortex-M board is chosen); Chris Simmonds, Mastering Embedded Linux Programming (week 13 and stretch work).
  • Software, all free: FreeRTOS as the teaching kernel, because it is small enough to read; Zephyr as the second kernel; GCC cross-compiler, GDB, OpenOCD or the board's own probe software, the board vendor's free IDE; sigrok and PulseView; QEMU; Buildroot; MCUboot; cppcheck for static analysis.
  • Industry norm: IAR Embedded Workbench and Arm Keil MDK as compilers and IDEs, SEGGER and Lauterbach debug probes, commercial trace viewers such as Percepio Tracealyzer, commercial MISRA checkers, and safety-certified kernels. With the free tools students miss certified tool chains, instruction-level trace and complete MISRA checking; they should know these exist and why regulated industries pay for them.
  • Hardware: a debug-capable microcontroller board per pair, logic analyser, sensor kit, current measurement; shared oscilloscopes and single-board Linux computers.

Notes for the instructor

In the planned public view this section is shown to the committee only (specification 3.4).

  • The usual failure: tasks that work alone and fail together, repaired by adding delays. A delay is not accepted as a fix; every delay in the project needs a written reason. The shared-resource table makes students look for the race before it bites.
  • Every timing claim needs a capture. This helps weaker students: toggle a pin, capture, read off the number is a concrete procedure, and scheduling theory is taught as timelines before formulas. The arithmetic needed is addition, division and rounding up.
  • Tool set-up is the largest early loss of time. Provide a prepared project that builds on day one and an installer or disk image for students' own computers. On a dual-core board, run the scheduling experiments on one core.
  • Assistants are useful for explaining kernel calls and fault registers and for drafting a driver skeleton from a datasheet excerpt. They are dangerous for concurrency: generated code shares variables between interrupt and task without protection, calls blocking functions in handlers, guesses stack sizes, and invents register names and bit positions. Such code runs on the bench and fails under load. Require the datasheet page in a comment beside every register access, and every shared object in the table.
