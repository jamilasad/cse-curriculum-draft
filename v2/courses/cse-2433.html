Rationale and what changed

The theory course absorbs Systems Analysis and Design from the 2022 syllabus: requirements, feasibility and analysis models are taught as the first third of software engineering, not as a separate subject. Together with the AI studio in semester 6, the studio replaces the four small development courses of 2022 (Software Development 1, Tools and Technologies for Internet Programming, Software Development 2 Lab, Software Engineering Lab) with one team product built in four stages. Theory topics are ordered to arrive when the studio needs them. Left out: the full UML notation set (four diagram types are kept), formal specification, CASE tools, and document templates for plan-driven projects. By hand first: in weeks 1–4 teams build a working application from HTTP handlers and raw SQL, with no AI and no framework that generates structure, so that every later tool replaces something the student has written once. With tools afterwards: a micro-framework, a TypeScript front end, a CI service and, from week 8, an AI pair programmer whose output is logged, tested and defended.

Minimum competency

  • Starting from an empty folder, write a server that handles GET and POST for one resource, stores it in a relational database with parameterised SQL, and returns HTML or JSON; explain every line.
  • Read one HTTP exchange in the browser's network tab or in curl output and state the method, path, status code, relevant headers, cookie and body.
  • Create a branch, commit, open a pull request, review a teammate's change with at least one substantive comment, and resolve a merge conflict.
  • Write unit tests for a given function, including boundary cases, and make a failing pipeline pass.
  • Demonstrate an SQL injection or a stored cross-site scripting attack on a given vulnerable page, and fix it.

Stretch goals

  • Add end-to-end browser tests (for example with Playwright) and automatic deployment to a staging environment on every merge.
  • Give the API pagination, versioning and rate limiting, publish an OpenAPI description, and build a third client (command-line or mobile) against it.
  • Get a pull request accepted by an open-source project and write up how the review went.

Weekly plan — studio

CSE-2434 Software Engineering Studio: Web Application Project · Studio / lab-only · 3 credits · 4 contact hours a week

Teams of four are formed by the instructor with mixed ability. The product is small: three or four related entities for a real or realistic client (a tuition centre, a hostel meal tracker, a clinic's appointments). The stage-1 server is written in a language the students already know (Python is recommended; Node.js is acceptable), using only the standard library's HTTP module and a plain database driver. JavaScript and TypeScript arrive in stage 3 with the front end.

Assessment

Theory (100). Written mid-term and final (80). At least half the marks are application and analysis, most of them on a short case such as a diagnostic centre's booking system: write user stories with acceptance criteria and draw a use-case or class diagram; design test cases with boundary values for a specified function; read a pull-request diff and write the review comments; find the smells in a code extract and refactor it; find and fix the vulnerability in a handler that builds SQL from user input; criticise a given API design; say what a given sequence of Git commands leaves in the repository; forecast from velocity data and say what could make the forecast wrong; choose a process model for a described project. Recall (definitions, lists of phases) is at most a fifth. Continuous assessment (20): Level 0 quizzes (10); two individual assignments (10), the student's own section of the studio product's requirements document and a written review of another team's pull request.

Studio (100). Team product against the four milestones 40 (10 each); individual contribution evidenced by commits and reviews 20; individual viva 20; documentation and demonstration 20. The contribution mark is read from the repository: commits spread over the semester, pull requests authored, reviews given, issues closed and, from week 8, the AI usage log. The paired-lab rule is applied here too: a student who cannot explain their own committed code in the viva does not pass the studio, whatever the team's mark.

Resources

  • Textbooks: Sommerville, Software Engineering; Pressman and Maxim, Software Engineering: A Practitioner's Approach; Dennis, Wixom and Roth, Systems Analysis and Design; Winters, Manshreck and Wright, Software Engineering at Google; Fowler, Refactoring; Chacon and Straub, Pro Git.
  • References: MDN Web Docs; the OWASP Top 10 and the OWASP Cheat Sheet Series.
  • Software, all free: Git with a GitHub or GitLab plan that includes issues, pull requests and CI; PostgreSQL; Python or Node.js for the server; TypeScript; curl and browser developer tools; pytest or the Node.js test runner; ESLint; ZAP for scanning; Nginx; a department Linux server or a free hosting tier for deployment.

Notes for the instructor

In the planned public view this section is shown to the committee only (specification 3.4).

  • Common failure: one or two students write everything. Form the teams yourself, rotate roles at each stage, require every member to own at least one user story end to end per milestone, and choose who explains what in walk-throughs.
  • Stage 1 works only if it is really unaided. Do most of it in scheduled hours on lab machines, ask for "explain this handler" without notice, and treat a team that cannot explain its code as not having reached Milestone 1.
  • Weaker students: no earlier course teaches HTML, CSS or JavaScript, so weeks 1 and 9 each open with a guided primer, and a worked handler from a different domain is given as a reference. Struggling teams may use plain JavaScript with type comments instead of TypeScript. Cut scope before quality.
  • AI from week 8: the usage log records what was asked, what was accepted, what was changed and how it was tested. Marks go to tests, review and explanation, not to the amount of code. Generated code is weakest on authorisation and error handling, which makes it good material for teaching review.

About this group of courses: Software, Data, AI and Security Core

These six packages run from semester 4 to semester 6 and carry the part of the core in which students build, secure, deploy and extend real software. Database Systems and the Software Engineering package share semester 4: the database course teaches SQL early enough for the studio to use it, and the web application built in the studio becomes an object that later courses return to. Artificial Intelligence & Machine Learning (semester 5) gives the foundations and the habit of honest evaluation that the AI Application & Agent Engineering Studio (semester 6) turns into a shipped product. In semester 6, Information Security attacks and hardens the semester-4 application and Distributed Systems & Cloud Computing containerises, deploys and monitors it, so each student meets the same piece of software as its builder, its attacker and its operator.
