Rationale and what changed

The 2022 syllabus had no course on running systems: Operating Systems explains the kernel, and nothing taught how to install, operate and recover a server for other people. This course does, and it is the base for the rest of the track and for Linux work in every other role. Each task is done three times: by hand on one machine to understand it, as a Bash or Python script, and as Ansible code applied to several machines, so that a student can rebuild a server from a repository. Troubleshooting is taught as a fixed method and practised every week on deliberately broken machines. The course runs beside the Cloud & DevOps Lab (CSE-3654) and leaves containers, Kubernetes and Terraform to it and to CSE-4787. Left out: Windows Server administration beyond a comparison, mail-server set-up, and performance tuning beyond first checks.

Minimum competency

Every passing student can, unaided, on a fresh virtual machine:

  • create users, groups, a shared directory and a sudo rule that together meet a stated access policy, and prove it by testing as each user;
  • add a disk, create an LVM logical volume with a file system, mount it persistently, extend it while mounted, and show that the machine still reboots cleanly;
  • set a static address, hostname and DNS server, open one service port in the firewall, and enable the service so that it survives a reboot;
  • find from systemctl status and journalctl why a service fails to start, and fix it;
  • write a Bash script that takes arguments, checks for errors and makes a dated backup of a directory, and restore a file from that backup.

Stretch goals

  • Test an Ansible role with Molecule and run the tests from a CI pipeline.
  • Investigate a slow server with the USE method (utilisation, saturation, errors) and write up the finding.
  • Sit RHCSA or LFCS.

Assessment

Theory. The written mid-term and final (80) give most marks to application and analysis: given journalctl output, name the cause and the fix; find the defects in a short Bash script; write the /etc/fstab line or LVM commands for a stated need; design users, groups and permissions for a described office; choose a backup scheme for a stated recovery point and recovery time; read an Ansible playbook and say what changes on its first and second runs. Recall takes at most a fifth of the marks. Continuous assessment (20): Level 0 quizzes in class (10); two assignments at Level 2 with disclosure (10): a hardening review of a supplied server, and a written runbook for one service.

Lab (100). Weekly lab work and record 30; two supervised practical tests 30; project 25; individual viva 15. The project, in pairs with named roles for each member: build a small organisation's servers (a web server behind a reverse proxy, a database, a file share, central logging and scheduled backup) on three VMs entirely from an Ansible repository; destroy the VMs and rebuild them from the repository in front of the examiner; restore the database from backup; hand in a runbook. In the viva each student explains and changes their own roles and scripts.

Resources

  • Main text: Evi Nemeth, Garth Snyder, Trent R. Hein, Ben Whaley and Dan Mackin, UNIX and Linux System Administration Handbook.
  • Supporting: Brian Ward, How Linux Works; William Shotts, The Linux Command Line (free to read online); Jeff Geerling, Ansible for DevOps; Al Sweigart, Automate the Boring Stuff with Python (free to read online); Thomas A. Limoncelli, Christina J. Hogan and Strata R. Chalup, The Practice of System and Network Administration (process and documentation).
  • Optional, for the certificate: Sander van Vugt, Red Hat RHCSA 9 Cert Guide.
  • Software, all free: VirtualBox, or KVM with virt-manager; Rocky Linux or AlmaLinux; Ubuntu Server; Ansible; ShellCheck; restic or BorgBackup; Lynis; OpenSCAP; PostgreSQL; Git. Lab PCs need memory for three small VMs; where they lack it, students use VMs on the department server.

Notes for the instructor

In the planned public view this section is shown to the committee only (specification 3.4).

  • Students break their machines often, and that is the point. Insist on a snapshot before each exercise so that recovery takes a minute rather than the session, and give each week a broken-machine image to diagnose.
  • Weaker students struggle most with not knowing where to look. Give a one-page card per topic (which commands show the state, where the logs are) and require the troubleshooting record in the same format every week; marks go to the method as well as to the fix.
  • Assistants are often wrong about distribution differences (dnf against apt, nmcli against netplan, firewalld against ufw) and about options that changed between versions. Use this in class: a student shows an assistant's draft, the group predicts what it will do, and it is then run on a snapshot.
  • Certification is optional. Do not let examination drill displace the rebuild, the runbook and the troubleshooting method, which employers test at interview.
