Rationale and what changed

A model in a notebook or a language-model demonstration is not a product. Much of the paid work lies in versioning, serving, monitoring, evaluation, cost control and risk, and the 2022 syllabus had no course on any of these. The studio introduced evaluation, cost and safety for one LLM feature; this course treats them as measured engineering practice, for predictive models and for LLM applications. It complements CSE-4805 Computing Ethics, Law & Society, taken in the same semester: that course covers law and professional ethics, this one covers what an engineer measures, tests and documents. Kubernetes administration, large-scale platform engineering and vendor ML platforms are left out. Students write a drift check and an evaluation harness in plain Python once before using a library for either. The course is designed for semester 8: two campus days a week, with part of the class away on Industry Practice for the first six weeks.

Minimum competency

Every passing student can, unaided:

  • Log the parameters, metrics and artefacts of a training run, and reproduce an earlier run from its record (code commit, data version, configuration).
  • Wrap a trained model in an HTTP service with input validation, run it in a container, and measure median and 95th-percentile latency under load.
  • Write a test set of at least 30 cases with pass criteria for an LLM feature, run it automatically, and decide from the results whether a new version may ship.
  • Compute the cost of a request from token counts and prices, and name two ways to reduce it.
  • Demonstrate a prompt-injection attack on a given retrieval application and add one control that stops it; compute one metric by group and state the gap.

Stretch goals

  • Deploy a new model version as a shadow or canary, with automatic rollback when a monitored metric falls.
  • Validate a model-based grader properly: agreement with human labels on at least 100 items, a revised rubric, and a published Bangla evaluation set with a datasheet.
  • Serve a quantised open-weight model yourself and work out, from measured throughput, the request volume at which it becomes cheaper than a hosted API.

Weekly plan — theory

Delivery is blended, as the framework intends for semester 8. Weeks 1–6 are taught live from the campus session, streamed and recorded, so that students on a six-week Industry Practice block can follow from their workplace. From week 7 all students attend on the two campus days. The mid-term examination and the Level 0 quizzes are held on campus, in week 7 or later.

WeekTopicsCLO
1Why ML systems fail in production: the life cycle; how they differ from ordinary software (dependence on data, non-determinism, silent failure); technical debt; two running cases: a credit-scoring model and a Bangla customer-support assistant. 5Cost and latency engineering: the cost model (per token, per request, per GPU-hour); shorter prompts and contexts; exact, semantic and provider-side caching; batching; routing between small and large models; distillation and quantisation; break-even between an API and self-hosting; capacity arithmetic2
6Monitoring and drift: operational metrics (latency, errors, saturation); data drift and concept drift; delayed labels; drift tests (population stability index, Kolmogorov–Smirnov, chi-square) and their false alarms; alerts, dashboards, incident review; when to retrain or roll back3

8Evaluating LLM systems I, test sets: why open-ended output is hard to score; what to measure (task success, faithfulness to sources, safety, format, tone); building test sets from real traffic, known failures, reviewed synthetic cases and adversarial cases; slices, including Bangla and code-mixed input; versioning; overfitting to the test set4
9Evaluating LLM systems II, graders: code-based checks (exact match, patterns, schema, execution); reference-based metrics and their limits; model-based graders: rubric design, pairwise against absolute scoring, grader bias, validation against human labels (agreement, Cohen's kappa); confidence intervals on small test sets; scoring retrieval separately from generation (recall@k, MRR)4
10Evaluating LLM systems III, human review and release: annotation guidelines and inter-annotator agreement; sampling live traffic for review; user feedback; A/B tests and guardrail metrics; evaluating agents (trajectory, tool calls, end state); evaluation as a release gate in CI; regression suites for when the underlying model version changes4
11Security of AI systems: threat modelling; direct and indirect prompt injection; jailbreaks; data exfiltration through tools; insecure handling of model output; excessive agency; poisoned training or retrieval data; model and dependency supply chain; defences: least privilege, allow-lists, input and output filtering, sandboxing, human approval, logging; the OWASP Top 10 for LLM Applications5
12Fairness: where bias enters (data, labels, measurement, deployment); group metrics (demographic parity, equal opportunity, equalised odds, calibration by group) and why they cannot all hold at once; mitigation before, during and after training; language systems: dialect, gender, romanised Bangla; cases: credit scoring, screening of job applicants6
13Safety and privacy: harm categories for a given application; content policy, guardrails and moderation; refusal and escalation to a human; controlling hallucination (grounding, citation, abstaining); red-teaming method; incident response; personal data in prompts, logs and training sets; vendor data terms; when sensitive data calls for a self-hosted model5
14Documentation and governance: model cards, datasheets, evaluation reports, risk registers; the NIST AI Risk Management Framework and the risk tiers of the EU AI Act in outline, as what foreign clients will ask about; audit trails and human oversight; the production-readiness review; review6

Weekly plan — lab

CSE-4884 ML Systems: MLOps, Evaluation & Responsible AI Lab · Lab · 1 credits · 2 contact hours a week

How the lab works with limited campus time: the lab has one two-hour slot on a campus day. Students on the six-week Industry Practice block are away in weeks 1–6, so those six labs are built to be done remotely. Each has a lab sheet, a starter repository and a recorded walkthrough, and is checked through commits and automated test output, not attendance. The campus session still runs every week for students who are on campus, and a one-hour online clinic serves those who are not. Week 7 includes a check-off of weeks 1–6 for returning students. Both supervised practical tests (weeks 8 and 13) and the viva (week 14) are held on campus, on lab machines, at Level 0. A student with no suitable computer off campus completes the remote sheets in open-lab hours on campus days, by week 9 at the latest. Employer code and data from Industry Practice must not be put into course repositories.

Compute: no GPU is needed. The lab uses a supplied reference system with two parts: a gradient-boosted credit model of the kind built in CSE-3673, and a small retrieval-based Bangla support assistant. The assistant calls either a quantised small open-weight model on CPU or a hosted API under a spending cap; recorded model outputs are supplied wherever a test must be repeatable. Services run in containers on a lab PC or a laptop, and a free hosting tier may be used for the project.

Assessment

Theory. Mid-term (weeks 1–7) and final, 80 marks. Most questions are short cases with numbers, so that at least half the marks are application and analysis: compute the cost of a request and of a month from token counts, prices and traffic, then cut it by a stated fraction and name the quality risk of the change; split a latency budget across the stages of a request; decide from two monitoring charts and a drift statistic whether to retrain, roll back or wait; decide from the pass rates of two versions on a small test set whether the difference is real; improve a weak grader rubric; design a test set for a described feature; mark the injection paths on an agent architecture diagram and place the controls; compute fairness metrics from confusion matrices by group and explain the trade-off; complete an unfinished model card. Recall carries at most a fifth of the marks. Continuous assessment, 20: three Level 0 quizzes on campus from week 7, best two counted (10); a two-page production-readiness review of a described system (10).

Lab (100). Weekly lab work and lab record 30 (for weeks 1–6 the record is the commit history and test output); two supervised practical tests 30 (15 each, offline documentation allowed); lab project 25; individual viva 15. The project, in teams of two or three, takes one AI system to production-ready standard: tracked and versioned, served, load-tested, monitored, with an evaluation suite as a release gate, a red-team report, a fairness or slice analysis, a cost sheet and a system card. The system is the AI part of the team's capstone where there is one, otherwise the reference system extended with a new feature. Only the operational layer added in this course is marked here; the product itself is marked in the capstone. A student who cannot explain their own submitted work in the viva does not pass the lab.

Resources

  • Textbooks: Huyen, Designing Machine Learning Systems; Huyen, AI Engineering; Gift and Deza, Practical MLOps; Barocas, Hardt and Narayanan, Fairness and Machine Learning. Papers and standards: Sculley et al., "Hidden Technical Debt in Machine Learning Systems"; Breck et al., "The ML Test Score"; Mitchell et al., "Model Cards for Model Reporting"; Gebru et al., "Datasheets for Datasets"; the OWASP Top 10 for LLM Applications; the NIST AI Risk Management Framework.
  • Software (free; current examples, reviewed at each offering): MLflow, DVC, FastAPI, Docker, ONNX Runtime, Locust, Prometheus and Grafana, Evidently, GitHub Actions, pytest, Fairlearn; the students' own evaluation harness first, then one open tool (promptfoo, DeepEval or Ragas); llama.cpp or Ollama for a local model; Label Studio for annotation (optional).
  • Models: a quantised small open-weight model, and a hosted API on a free tier or under a spending cap. The specific models and prices are set each semester.

Notes for the instructor

In the planned public view this section is shown to the committee only (specification 3.4).

  • With two campus days and part of the class away, students fall behind without anyone noticing. Require a commit every week, check the history weekly, contact any student who has been silent for two weeks, and treat the week 7 check-off as a fixed checkpoint. Hold no Level 0 assessment online.
  • AI assistants produce container files, CI files and service code on request, so that code earns few marks. Marks go to measurements, evaluation results and decisions. The particular danger in this course is a student who lets a language model write both the test set and the grader and then trusts them; the hand-labelled items and agreement figures in week 10 are there to prevent it.
  • The reference system is supplied in working order and each lab adds one layer, so a mid-level student who found model training hard can still succeed here. Give a checklist for each lab and a filled-in example of each document, since the model card and risk table are new kinds of writing for most students.
  • Tools and prices change every year. Teach the practices (tracked, versioned, tested, monitored, evaluated, documented) and update the tool list and the cost arithmetic at each offering. Agree with the teacher of CSE-4805 which cases each course covers, so that the two do not repeat each other.
