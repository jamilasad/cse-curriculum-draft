Minimum competency

Every passing student can, unaided:

  • Log the parameters, metrics and artefacts of a training run, and reproduce an earlier run from its record (code commit, data version, configuration).
  • Wrap a trained model in an HTTP service with input validation, run it in a container, and measure median and 95th-percentile latency under load.
  • Write a test set of at least 30 cases with pass criteria for an LLM feature, run it automatically, and decide from the results whether a new version may ship.
  • Compute the cost of a request from token counts and prices, and name two ways to reduce it.
  • Demonstrate a prompt-injection attack on a given retrieval application and add one control that stops it; compute one metric by group and state the gap.

Stretch goals (from the outline)

  • Deploy a new model version as a shadow or canary, with automatic rollback when a monitored metric falls.
  • Validate a model-based grader properly: agreement with human labels on at least 100 items, a revised rubric, and a published Bangla evaluation set with a datasheet.
  • Serve a quantised open-weight model yourself and work out, from measured throughput, the request volume at which it becomes cheaper than a hosted API.

Section 7 says where in the semester a strong student can take each one up.

2. Class pattern and semester-8 delivery

Assumption to confirm (README A1–A3).

  • Theory: 3 contact hours a week, given as two 90-minute classes. That makes 28 classes in 14 teaching weeks.
  • Lab: one 2-hour session a week, 14 sessions.
  • The mid-term (weeks 1–7) and the final are held outside the 14 teaching weeks. The mid-term is on campus in the examination week after teaching week 7, as the outline requires ("in week 7 or later").
  • The department may re-split theory into three 60-minute classes. README A2 says how.

Semester-8 rule (framework section 10). Weeks 1–6 use only work that can be done remotely. Every supervised test, Level 0 quiz, the mid-term and the viva fall in weeks 7–14, on campus.

The two running cases appear in almost every class:

  • Case C (credit): a gradient-boosted credit-scoring model for a microfinance lender, of the kind built in CSE-3673.
  • Case A (assistant): a retrieval-based Bangla customer-support assistant that answers questions about repayments.

Both match the parts of the lab's reference system.

Class 1 (Week 1): Why ML systems fail in production

  • Outline topics covered: Why ML systems fail in production: the life cycle; how they differ from ordinary software (dependence on data, non-determinism, silent failure); technical debt; two running cases: a credit-scoring model and a Bangla customer-support assistant.
  • CLO / PO: CLO1 / PO5

50–70Short lecture: how ML systems differ from ordinary software (they depend on data; outputs vary between runs; they fail silently). Technical debt from Sculley et al.: glue code, pipeline jungles, configuration debt, undeclared consumers, feedback loops

  • Formative check (online poll): "Over three months the credit model's approval rate rises slowly. The service shows no errors. Is this a crash, a silent failure, or normal?" Expected: a silent failure until shown otherwise; the inputs or the population may have changed; it needs input and outcome monitoring, not only error monitoring.
  • Homework: read Sculley et al. Write 150 words on one debt type you saw in your own CSE-3673 or capstone work, posted in the course forum (Level 2; unmarked; remote).

Common arrangements

The reference system (supplied in working order; each lab adds one layer):

  • the credit model: a gradient-boosted model on a synthetic microfinance loan dataset built by the instructor, with group attributes (for example region and gender) that are synthetic, not real people;
  • the assistant: a small retrieval-based Bangla support assistant over about a hundred short policy documents written for the course. It calls either a quantised small open-weight model on CPU (llama.cpp or Ollama) or a hosted API through the department's capped key (README A9). A file of recorded model outputs is supplied, so that any test can be repeated without calling a model.

Compute. No GPU is needed. Services run in containers on a lab PC or a laptop. A free hosting tier may be used for the project. Lab PCs run one container stack at a time.

Weeks 1–6 are remote-capable (outline; framework section 10). Each of Labs 1–6 has:

  • a lab sheet (template T3) and a starter branch in the course repository organisation;
  • a recorded walkthrough of 15–25 minutes, posted before the campus session;
  • a one-hour online clinic each week, run by the lab instructor at a time fixed in week 1 (an evening slot, so that block students can attend after work);
  • an automated check script in the repository (checks/labNN.py) that tests the deliverable and writes checks/labNN-result.txt, which the student commits;
  • a deadline: the deliverable, the result file and the lab record page (T6) are committed before the start of the next lab session.

The campus session still runs every week for students on campus. It follows the timed plan in each entry. Remote students follow the same steps from the sheet and the recording.

Marking of weeks 1–6. The record is the commit history and the automated test output (outline). The instructor reads the history weekly and gives informal feedback. The R1 marks for Labs 1–6 are confirmed at the week 7 check-off, where the record-and-explanation point needs a spot question answered in person.

Marking notes. Cost: 1,500 × 0.40 / 1,000,000 + 200 × 1.60 / 1,000,000 = 0.0006 + 0.00032 = 0.00092 dollars per request. Requests per day: 15,000 × 3 = 45,000. 6.4 Sample questions with answers and marking notes

All prices and organisations are made up for the exercise.

Recall (mid-term 1a, 2 marks). "Name four things you must record so that a training run can be reproduced."

  • Answer: the code commit, the data version, the configuration including settings and the seed, and the environment (library versions or container image).
  • Marking: half a mark each.

Understanding (mid-term 2, 4 marks). "Explain training–serving skew using Case C. How does a registry entry with a recorded reason help?"

  • Answer: skew is a difference between how inputs are prepared in training and at serving. Example: missing income was filled with the median in training, but the app sends 0. The model then scores those applicants as having no income. A registry entry links the model to its run, data version and pre-processing, so the serving code can be checked against them. The recorded reason shows what evidence the promotion relied on.
  • Marking: definition 1; correct example 1; consequence 1; registry role 1.

Application (mid-term 3, 7 marks). "Each request uses 1,200 input tokens and 250 output tokens. Prices: 0.50 dollars per million input tokens, 1.50 per million output tokens. Traffic: 20,000 requests a day. (a) Compute the cost per request and per 30-day month. (b) Cut the monthly cost by 40% with two changes and name one quality risk."

  • (a) 1,200 × 0.50 / 10⁶ = 0.00060; 250 × 1.50 / 10⁶ = 0.000375; total 0.000975 dollars a request. Month: 0.000975 × 20,000 × 30 = 585 dollars. (5 marks: input cost 1, output cost 1, per request 1, month 2.)
  • (b) Target 351 dollars. Example: trim the retrieved context from 700 to 300 tokens, so input is 800 tokens: 0.00040 + 0.000375 = 0.000775. Add an exact cache with a 25% hit rate: 0.000775 × 0.75 = 0.000581 a request, about 349 dollars a month. Risk: less context can lower faithfulness; a cache can serve stale answers after a policy change. (2 marks: a combination that reaches the target 1, a correct risk 1.)

Analysis (mid-term 4, 4 marks). "Twenty measured latencies, in milliseconds, sorted: 120, 135, 140, 150, 155, 160, 160, 170, 175, 180, 185, 190, 200, 210, 230, 260, 300, 420, 650, 900. The target is a 95th percentile under 500 ms. (a) Compute the median and the 95th percentile. Is the target met? (b) The logs show that all requests over 400 ms came in the first minute after a new instance started. Name the likely cause and two fixes."

  • (a) Median = (180 + 185) / 2 = 182.5 ms. 95th percentile by the nearest-rank method: rank 0.95 × 20 = 19, the 19th value, 650 ms. Target not met. (The mean is 254.5 ms and hides this.) (2 marks.)
  • (b) Cold starts: the model loads on the first request. Fixes: load the model at start-up and route traffic only after the health check passes; keep a minimum number of warm instances. (2 marks.)

Application and evaluation (mid-term 5, 6 marks). "Income bins for Case C. Reference shares: 0.25, 0.25, 0.25, 0.25. This month: 0.10, 0.20, 0.30, 0.40. (a) Compute the population stability index. (b) The PSI rose in the month that twelve rural branches opened. Latency and errors are flat. The approval rate rose from 62% to 71%. Repayment labels arrive after three months. No new model was released. Retrain, roll back or wait?"

  • (a) PSI = Σ (actual − expected) × ln(actual / expected).
    • Bin 1: (0.10 − 0.25) × ln(0.4) = (−0.15) × (−0.916) = 0.137
    • Bin 2: (0.20 − 0.25) × ln(0.8) = (−0.05) × (−0.223) = 0.011
    • Bin 3: (0.30 − 0.25) × ln(1.2) = 0.05 × 0.182 = 0.009
    • Bin 4: (0.40 − 0.25) × ln(1.6) = 0.15 × 0.470 = 0.071
    • PSI ≈ 0.23. A common rule of thumb reads 0.1 to 0.25 as a moderate shift. (3 marks: formula 1, bins 1, total 1.)
  • (b) Not roll back: no new version was released. Not retrain yet: there are no labels for the new population, and retraining on old data does not help. Wait, but act: check the pipeline for a unit or coding change; compare drift by branch; send new-branch applications above a set amount to human review; set a review date when early-repayment signals arrive. (3 marks: rejects roll back with reason 1; rejects blind retraining with reason 1; a concrete watch-and-act plan 1.)

Analysis (mid-term 6, 4 marks). "Which test catches each fault: (a) the income column arrives in thousands of taka; (b) the score changes when only the applicant's name changes; (c) a refactor breaks the date parser; (d) a retrained model's AUC falls from 0.78 to 0.70?" Answer: (a) data validation (range check); (b) behavioural (invariance) test; (c) unit test; (d) minimum-performance test against a stated floor. One mark each, with a reason.

Application (final 5a, 4 marks). "Two people label 40 answers pass or fail. Both pass: 22. Both fail: 10. A pass, B fail: 5. A fail, B pass: 3. Compute Cohen's kappa."

  • Observed agreement: (22 + 10) / 40 = 0.80.
  • A passes 27 of 40 (0.675); B passes 25 of 40 (0.625).
  • Chance agreement: 0.675 × 0.625 + 0.325 × 0.375 = 0.422 + 0.122 = 0.544.
  • Kappa = (0.80 − 0.544) / (1 − 0.544) = 0.256 / 0.456 ≈ 0.56. Usually described as moderate agreement: the guideline needs work before a grader is checked against it.
  • Marking: observed 1; marginals 1; chance 1; kappa and comment 1.

Analysis (final 5b, 4 marks). "On the same 60 cases, version 1 passes 45 and version 2 passes 50. Version 2 fixes 8 cases that version 1 failed and breaks 3 that version 1 passed. Is version 2 really better?"

  • Unpaired view: 75% against 83.3%. Standard error of the difference ≈ √(0.75 × 0.25 / 60 + 0.833 × 0.167 / 60) ≈ 0.074. 95% interval ≈ 0.083 ± 0.145, from −0.06 to 0.23. It includes zero.
  • Paired view (better, same cases): 8 fixed against 3 broken. McNemar statistic (8 − 3)² / (8 + 3) = 2.27, below 3.84, the 5% critical value.
  • Conclusion: not shown to be better on this test set. Look at the 3 broken cases: if any is critical, block the release. Add cases to the slices that changed.
  • Marking: an interval or paired test computed correctly 2; correct conclusion 1; attention to the broken cases 1.

Evaluation (final 6, 4 marks). "Improve this grader rubric: 'Rate the answer from 1 to 10 for quality.'"

  • A good answer: separate criteria, each pass or fail with a definition. Faithful: every factual claim is supported by a retrieved passage. Answers the question asked. Replies in the customer's language and script. Reveals no other customer's data. Escalates when the policy requires. Give one passing and one failing example per criterion. Ask the grader to quote the supporting passage before its verdict. Return JSON. Check the grader against human labels.
  • Marking: criteria separated and defined 2; examples or evidence requirement 1; validation against people 1.

Analysis (final 7, 6 marks). "Case A agent: the user's chat goes to an orchestrating model with four tools: (1) search over policy documents, including PDFs uploaded by customers; (2) get_balance, reading the loan database; (3) send_email; (4) fetch_url for web pages. The answer is shown in the app as HTML. Mark every injection path and place a control on each."

  • Paths: direct injection in the chat; indirect injection through uploaded PDFs and fetched web pages; exfiltration through send_email and through links or images in the HTML answer; get_balance used for another customer if the model supplies the id; HTML output that can run scripts.
  • Controls: the customer id comes from the session on the server; send_email only to the logged-in customer's verified address, or with human approval; strip or escape HTML, links and images in the output; treat retrieved and fetched text as data and keep it apart from instructions (noting this is weak alone); an allow-list for fetch_url or remove it; log all tool calls.
  • Marking: one mark per correct path with its control, up to 6.

Application and evaluation (final 8, 6 marks). "Credit model, positive = 'approve'. Group A: TP 90, FP 20, FN 30, TN 60. Group B: TP 50, FP 10, FN 50, TN 90. (a) Compute selection rate, true-positive rate, false-positive rate and precision for each group. (b) The lender lowers group B's threshold until its true-positive rate is 0.75. What is gained and what is the cost?"

  • (a) Group A: selection (90 + 20) / 200 = 0.55; TPR 90 / 120 = 0.75; FPR 20 / 80 = 0.25; precision 90 / 110 = 0.82. Group B: selection 60 / 200 = 0.30; TPR 50 / 100 = 0.50; FPR 10 / 100 = 0.10; precision 50 / 60 = 0.83. Demographic parity gap 0.25; equal-opportunity gap 0.25; precision nearly equal. The base rates differ (0.60 against 0.50), so not all criteria can hold. (4 marks.)
  • (b) More creditworthy applicants in group B are approved. Group B's false-positive rate also rises, so more loans in group B default, and precision falls. Group-specific thresholds may raise legal questions (CSE-4805). (2 marks.)

Creation (final 9, 3 marks). "This model card for Case C lacks 'Out-of-scope uses', 'Metrics by group' and 'Caveats'. Write them." Marking: out-of-scope uses specific to this model (for example small-business loans, branches it has not seen, interest-rate setting) 1; metrics by group with counts and the gaps from Question 8 1; caveats a manager can act on (drift from new branches; labels arrive late; vendor threshold not reviewed) 1.

7. Support for weaker students

The outline notes that the reference system is supplied in working order and each lab adds one layer, "so a mid-level student who found model training hard can still succeed here". The measures below build on that.

Keeping remote students from falling behind (weeks 1–6).

  • The lab instructor runs a script each week that lists students with no commit and no check result for the week. A student silent for two weeks is contacted by phone or message (outline), and a catch-up plan is agreed.
  • Recorded walkthroughs for every lab, and an evening online clinic, so that block students can work after their working day.
  • The week 7 check-off is a fixed checkpoint. Students behind at that point are booked into open-lab hours with a dated plan to finish by week 9.

For each lab.

  • A one-page checklist of what "done" means (for example Lab 3: schema with ranges; health endpoint; three invalid-input tests; image without secrets; check script passing).
  • A filled-in example of each new kind of document: a promotion note, a latency report, a cost sheet, an incident note, a risk table, a model card and a system card (outline note). Students write their own by changing the example, not from a blank page.
  • Sentence frames for the review and the system card (README T8, R5).
  • The recorded-output mode, so that a student without a working API key or a fast computer can still complete every lab.

Numbers sheets. This course is mostly arithmetic on short cases. One sheet each for: cost per request and per month; latency percentiles and budgets; capacity; break-even; PSI; Cohen's kappa; an interval for a pass rate; recall@k and MRR; metrics by group. Each sheet has three worked examples and five practice problems with answers. They are released with the class where the topic is taught and used in the clinics.

Early warning. After Quiz 1, the mid-term and practical test 1: any student below 40% meets the teacher and gets a written plan of two or three actions (README section 6).

Teams. Teams of two or three are checked in week 7 so that every team has at least one member comfortable with containers and CI. Where a team is the capstone team's AI part, the capstone supervisor is told who does what.

Language. Teachers may explain in Bangla in clinics. Written answers are marked for content (README A7). The class glossary is extended with this course's terms (drift, canary, grader, injection, kappa).

For the strong 15% (stretch goals from the outline).

  • Shadow or canary deployment with automatic rollback: start after Lab 7 and Class 14; build it into the project.
  • A properly validated model-based grader (at least 100 human-labelled items, a revised rubric, a Bangla evaluation set with a datasheet): start after Lab 10; it can become the project's evaluation part.
  • Self-hosting break-even from measured throughput: start after Lab 5 and Class 10.
  • Recognised through the "Strong" level of the project rubric, not with marks beyond 100.

9. Issues for the committee

These are reported, not fixed.

  1. Conflict on the Track IV lab in weeks 1–6. The CSE-4810 Industry Practice package ("Timetables", in courses/50-professional-capstone-practice.md) says that classes that cannot run online, naming the Track IV lab, must be given to block students in weeks 7–14 in a compressed section. The CSE-4884 outline instead makes lab weeks 1–6 remote-capable, checked through commits and test output. This plan follows the CSE-4884 outline. The committee should decide which rule holds for the AID track and correct the other text. If the compressed section is kept, it needs staff time and a room in weeks 7–14.
  2. Team size against the capstone. The CSE-4884 project is for teams of two or three, and may be the AI part of the team's capstone. Capstone teams are three or four (framework section 11; capstone shared design). A capstone team of four cannot be one CSE-4884 team. The committee should decide whether a four-member capstone team splits into two lab teams on different operational parts, or whether a lab team of four is allowed for capstone-based projects.
  3. Week 14 congestion in semester 8. In week 14, on two campus days, students have the Capstone Project II showcase and final defence (M8, "on campus within week 14"), Industry Practice vivas, and this course's production-readiness review and individual viva. The CSE-4884 review and viva alone need about six and a half hours of panel time for a section of 30 (Lab 14). The department must timetable extra slots, possibly in the examination period, and say whether vivas may run outside the lab slot.
  4. Lab week 7 is overloaded. One 2-hour session holds the in-person check-off of six remote weeks (about 2–3 minutes a student, about 60–90 minutes for 30 students), a new CI pipeline with a deliberately failed run, and the project plan. This plan pre-marks from commits and runs the check-off in parallel with the CI work, but the instructor cannot also help students with CI. A second staff member in that session, or moving the check-off to an extra slot in week 7, would fix it.
  5. The same work may be marked twice. Only the operational layer is marked in CSE-4884 (outline), but the Capstone Project II plan also covers monitoring and hardening (week 12) and its rubric rewards a system that is "monitored". A team whose CSE-4884 project is its capstone system could be credited for the same monitoring in both courses. The committee should state whether this is acceptable, or how the two markers divide the evidence.
  6. Open-lab route by week 9. A student without a suitable computer off campus completes the six remote sheets in open-lab hours on campus days by week 9 (outline). In weeks 7–9 those students also have Lab 7, practical test 1, Lab 9, the mid-term and other courses, on two campus days. The department should say when open-lab hours run and whether laptops can be lent to these students for weeks 1–6.
  7. EU AI Act not in the Resources. The week 14 topic names the risk tiers of the EU AI Act, but the outline's Resources list the NIST AI RMF and not the Act. The teacher needs a short summary from the official text; the committee may want to add it to the Resources.
  8. Hosted API budget. The reference assistant and Labs 5 and 10 use a hosted API under a spending cap. Framework section 16 has no budget line for this (see README section 9, issue 2).
