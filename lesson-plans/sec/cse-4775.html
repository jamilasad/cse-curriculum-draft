1.3 Minimum competency

Every passing student can, unaided:

  1. Capture and modify a request with an intercepting proxy, and demonstrate one injection flaw and one access-control flaw on a lab target.
  2. Given a short vulnerable code fragment (SQL injection, stored cross-site scripting, or a missing authorisation check), identify the flaw and write the fix.
  3. Explain how a cookie or token authenticates a request and name the settings that protect it.
  4. Run a static-analysis tool and a dependency scanner on a repository and say which findings matter and why.
  5. Write one finding in standard form: title, affected component, steps to reproduce, impact, severity, recommended fix.

2. Class pattern (assumption to confirm)

  • Theory: 3 contact hours a week as two 90-minute classes (A and B): 28 classes in 14 teaching weeks.
  • Lab: one 2-hour session a week: 14 sessions.
  • Mid-term and final are held outside the 14 teaching weeks (mid-term after week 7) unless the outline says otherwise. The outline does not say otherwise.
  • The department may re-split theory into three 60-minute classes; README section 3 gives the mapping.

Course-specific notes:

  • Language of code examples. Code in classes, quizzes and examinations is in JavaScript or TypeScript with SQL, the language of the semester-4 studio (framework section 5), so that weaker students read familiar syntax. A few examples in Python or Java show that the flaw classes are the same in every language.
  • By hand first. Each flaw is exploited by hand with an intercepting proxy (Burp Suite Community Edition or ZAP) before any scanner is used, and code is reviewed by hand before static-analysis tools are run on it. The class plans and lab sessions follow this order.
  • Every weekly lab has three steps (outline instructor note): exploit with guidance, explain the root cause in two sentences, fix and retest.
  • Public targets for practice, department-built targets for assessment. OWASP Juice Shop, DVWA, WebGoat and crAPI are used for practice. Both supervised practical tests and the project use the department's own unseen targets. Marks go to the explanation and the fix, not to a captured flag.
  • SWE students take this course as a listed substitution and have not used the track range or CSE-3675. They receive the range guide and the rules of engagement (T1, schedule B) one week before week 1 and may attend a one-hour set-up clinic. Nothing from CSE-3675 is assumed in any class or lab.
  • CSE-3651 material is used, not re-taught. Password hashing, cryptography, and the overview of the OWASP Top 10 come from CSE-3651. Where a class needs them, it gives a two-minute reminder and moves on.
  • Severity. Examples use CVSS version 3.1 base metrics. The department should fix one CVSS version for the whole track (see section 9).

3.2 Classes

Every formative check is ungraded and at Level 0. Every homework is at AI Level 2 (the assignments' level) unless it says otherwise; a T6 log is needed only for graded work. "Local target" always means a department-supplied target running on the student's own machine, bound to localhost, or in the track range.

Week 1

Class 1 (Week 1, A): How a web application looks to an attacker

  • CLO (PO): CLO1 (PO1, PO2)
  • Contents and timing (90 min):
    • 0–10 min: Course introduction: what the course is for, the "by hand first" rule, how marks are earned, the one-sentence boundary: "every exploit runs only against department-supplied targets". The full boundary comes in class 2 and lab 1.
    • 10–35 min: Short lecture: an HTTP request and response line by line (method, path, query string, headers, body, status code); HTTP is stateless; how cookies are set with Set-Cookie and sent back by the browser.
    • 35–55 min: Live demonstration on a local OWASP Juice Shop through an intercepting proxy: log in, search for a product. Students read the captured requests on the screen and name each part aloud.
    • 55–75 min: The same-origin policy and CORS: an origin is scheme, host and port; the policy stops a page from reading another origin's responses, not from sending requests; CORS response headers relax it; the common mistake is reflecting any Origin while allowing credentials. Think-pair-share on six pairs of URLs: same origin or not?
    • 75–85 min: Trust boundaries: browser, web server, database, third-party API, administrator panel. Draw where data crosses from less trusted to more trusted.
    • 85–90 min: Formative check and homework.
  • TLA: Short lecture; live proxy demonstration on a local target; think-pair-share; board diagram of trust boundaries.
  • Materials and readings: Zalewski, The Tangled Web (HTTP, cookies, the same-origin policy); Hoffman, Web Application Security (the structure of a modern web application); teacher's slides; local Juice Shop; Burp Suite Community Edition or ZAP.
  • Formative check: Exit ticket: three URL pairs (same origin or not) and one CORS response (Access-Control-Allow-Origin echoing the request origin with Access-Control-Allow-Credentials: true): is it safe, and why not?
  • Homework: Install Docker and the local targets from the range guide on your own laptop if you have one, with every port bound to localhost only. Read The Tangled Web on the same-origin policy. AI Level 2.

Class 2 (Week 1, B): Attack surface, threat modelling, the legal boundary and the standard form of a finding

  • CLO (PO): CLO1 (PO1, PO2); CLO6 (PO4, PO9)
  • Contents and timing (90 min):
    • 0–5 min: Recap: the parts of a request.
    • 5–20 min: Mapping the attack surface: pages, parameters, headers, cookies, file uploads, API endpoints, administrator paths, roles, data stores. Manual browsing through the proxy before any automatic spidering; recording a site map.
    • 20–45 min: Threat modelling: data-flow diagram elements (external entity, process, data store, data flow, trust boundary); STRIDE per element. Worked example: a small MFS agent portal (an agent logs in, records a cash-in, the customer receives an SMS). Then groups of four draw a data-flow diagram of a university result portal and list six STRIDE threats.
    • 45–65 min: Legal boundary, scope and rules of engagement: written authorisation is what separates a test from an offence; good intentions are not a defence; scope lists targets, times, accounts and forbidden actions. The course boundary (T1 schedule B): department targets only; no internet site, university system or other student's application; bug-bounty work is not part of the course. Case discussion of three short situations: a friend asks you to "check" his shop's website; you notice that the university portal shows another student's ID in the address bar; a public walkthrough tells you to try a payload on a live demonstration site. For each: what do you do, and why?
    • 65–85 min: The standard form of a finding (T5): title, affected component, steps to reproduce, impact, severity, evidence, recommended fix, retest. The class rewrites a poor example ("XSS found, very dangerous, fix it") together.
    • 85–90 min: Release Assignment 1 (threat model); formative check.
  • TLA: Short lecture; worked example; group data-flow diagram; case discussion; joint rewriting of a bad finding.
  • Materials and readings: Shostack, Threat Modeling: Designing for Security (data-flow diagrams and STRIDE); Stuttard and Pinto, The Web Application Hacker's Handbook (mapping the application); T1 schedule B; T5; the Assignment 1 brief.
  • Formative check: Each student writes one STRIDE threat for the result portal in one sentence, naming the element it affects; the teacher reads five aloud and corrects them.
  • Homework: Start Assignment 1 (due class 7). Tell the teacher by class 3 which feature of your semester-4 application you will model; students from the same semester-4 team must choose different features. AI Level 2.

Week 2

Class 3 (Week 2, A): SQL injection I: in-band, blind and second-order; mixing code and data

  • CLO (PO): CLO1 (PO1, PO2); CLO2 (PO2, PO3)
  • Contents and timing (90 min):
    • 0–10 min: Entry questions on the board (ungraded): what does a browser send with every request to the same site? What does the same-origin policy not stop?
    • 10–30 min: Root cause: a query is built by joining strings, so the database parser cannot tell the programmer's code from the user's data. Trace one concatenated query on the board with a normal value and with a quote character.
    • 30–50 min: In-band injection: error-based and UNION-based; finding the number of columns; reading another table. Shown by the teacher on local DVWA; students do it themselves in lab 2.
    • 50–65 min: Blind injection: boolean-based and time-based; the attacker learns one fact per request; why tools automate it.
    • 65–80 min: Second-order injection: a value is stored safely and later used unsafely (for example a username used in a password-change query). Pairs trace a two-step code path and find where the flaw is.
    • 80–90 min: Formative check.
  • TLA: Board tracing; teacher demonstration on a local target; pair code tracing.
  • Materials and readings: Stuttard and Pinto, The Web Application Hacker's Handbook (attacking data stores); OWASP Cheat Sheet Series (SQL injection prevention); local DVWA.
  • Formative check: A five-line handler is shown. Students write on a mini-whiteboard the line where data becomes code.
  • Homework: Read the OWASP SQL injection prevention cheat sheet. Write, by hand, the query that a given input produces for three inputs. AI Level 2; do it unaided first, as Quiz 1 covers it.

Class 4 (Week 2, B): SQL injection II: parameterised queries, ORMs and NoSQL injection

  • CLO (PO): CLO2 (PO2, PO3)
  • Contents and timing (90 min):
    • 0–10 min: Recap with two cold-call questions on in-band and blind injection.
    • 10–35 min: Parameterised queries: placeholders in a Node.js database driver, PreparedStatement in Java, parameters in Python; why the database treats the value as data. What cannot be a parameter: table names, column names, sort direction; use an allow-list for these.
    • 35–55 min: Where ORMs still fail: raw-query functions, string-built where clauses, sort fields taken from the request, query objects built directly from request JSON. Pairs read four ORM snippets and mark each safe or unsafe with a reason.
    • 55–75 min: NoSQL injection: operator injection in a JSON login body (an object such as {"$ne": null} where a string was expected); fix with type checks and schema validation of the request body.
    • 75–85 min: Defence in depth: a least-privilege database account; generic error messages.
    • 85–90 min: Formative check and homework.
  • TLA: Short lecture with code on screen; pair code reading; whole-class correction.
  • Materials and readings: Hoffman, Web Application Security (injection and defending against it); OWASP Cheat Sheet Series (query parameterisation); teacher's code snippets.
  • Formative check: Rewrite one concatenated query as a parameterised query on paper; the teacher checks three at random.
  • Homework: Revise classes 1–4 for Quiz 1 in class 5. AI Level 2; practise unaided, as the quiz is Level 0.

Week 3

Class 5 (Week 3, A): OS command injection and server-side template injection (Quiz 1)

  • CLO (PO): CLO1 (PO1, PO2); CLO2 (PO2, PO3)
  • Contents and timing (90 min):
    • 0–15 min: Quiz 1 (Level 0, 10 marks): weeks 1–2.
    • 15–40 min: OS command injection: a program passes user input to a shell; shell metacharacters join a second command. Safe APIs run a program with an argument list and no shell (execFile in Node.js, a list of arguments in Python's subprocess); allow-list validation as a second layer.
    • 40–65 min: Server-side template injection: user input becomes part of the template instead of data passed to it; detection on a local target with a harmless arithmetic expression; why the result can be code execution; fixes: never build templates from input, use logic-less templates, keep data and template apart.
    • 65–85 min: Pairs read five snippets (two command calls, two template renders, one file read) and mark each safe or unsafe with the reason.
    • 85–90 min: Formative check.
  • TLA: Level 0 quiz; short lecture; teacher demonstration; pair code reading.
  • Materials and readings: Stuttard and Pinto, The Web Application Hacker's Handbook (injecting into back-end components); OWASP Cheat Sheet Series (OS command injection defence).
  • Formative check: Thumbs up or down on three one-line calls: does a shell run here?
  • Homework: For one snippet from today, write the fixed version and a test input that proves the fix. AI Level 2.

Class 6 (Week 3, B): File handling flaws; validation, encoding and safe APIs compared

  • CLO (PO): CLO1 (PO1, PO2); CLO2 (PO2, PO3)
  • Contents and timing (90 min):
    • 0–5 min: Recap.
    • 5–25 min: Path traversal: ../ sequences, encoded forms, absolute paths; the fix is to map an identifier to a file name on the server, or to resolve the full path and check that it stays inside the allowed folder.
    • 25–40 min: File inclusion: a page includes a file named in the request (as in DVWA's PHP pages); why it can run attacker-chosen code; fix with a fixed list.
    • 40–60 min: Unsafe file upload: trusting the content type or extension, saving into the web root, keeping the user's file name; the fix: store outside the web root with a random name, check the type by content against an allow-list, limit size, serve with safe headers.
    • 60–80 min: The class builds a comparison table on the board: input validation (allow-list), output encoding and safe APIs. For each flaw met so far, which control removes the root cause and which only helps? Think-pair-share, then whole-class.
    • 80–90 min: Formative check and homework.
  • TLA: Short lecture with examples; whole-class table building; think-pair-share.
  • Materials and readings: Hoffman, Web Application Security (defending against injection; secure file handling); OWASP Cheat Sheet Series (file upload; input validation).
  • Formative check: Exit ticket: "Why does input validation alone not stop SQL injection in a free-text comment field?" in two sentences.
  • Homework: Read the OWASP input validation cheat sheet. Continue Assignment 1. AI Level 2.

Week 4

Class 7 (Week 4, A): Cross-site scripting I: reflected, stored and DOM-based

  • CLO (PO): CLO1 (PO1, PO2)
  • Contents and timing (90 min):
    • 0–10 min: Assignment 1 due (submitted to the course repository before class). Recap.
    • 10–35 min: How cross-site scripting works: the attacker's script runs inside the victim's page, in the site's own origin, so the same-origin policy does not help. Reflected, stored and DOM-based. Sources (location, document.referrer, stored data) and sinks (innerHTML, document.write, eval, href attributes).
    • 35–55 min: Teacher demonstration on local DVWA and Juice Shop: a harmless alert for reflected and stored cases, then a DOM-based case; then show impact: reading a cookie that lacks HttpOnly, acting as the user.
    • 55–75 min: Pairs trace four short front-end snippets from source to sink and say which type each is.
    • 75–85 min: Impact in a real setting: what an attacker gains with stored script in an MFS agent portal.
    • 85–90 min: Formative check.
  • TLA: Short lecture; teacher demonstration on local targets; pair source-to-sink tracing; case discussion.
  • Materials and readings: Stuttard and Pinto, The Web Application Hacker's Handbook (attacking users: cross-site scripting); Zalewski, The Tangled Web (script execution and the DOM).
  • Formative check: Mini-whiteboard: name the type (reflected, stored, DOM) for three one-line descriptions.
  • Homework: Read the OWASP cross-site scripting prevention cheat sheet. AI Level 2.

Class 8 (Week 4, B): Cross-site scripting II: encoding by context, Content Security Policy, limits of auto-escaping

  • CLO (PO): CLO1 (PO1, PO2); CLO2 (PO2, PO3)
  • Contents and timing (90 min):
    • 0–5 min: Recap.
    • 5–30 min: Output contexts: HTML body, HTML attribute, JavaScript string, URL, CSS. Each needs its own encoding; one "escape" function is not enough. The cheat sheet's rules.
    • 30–50 min: Framework auto-escaping and where it stops: raw HTML features (dangerouslySetInnerHTML, v-html, a template's "safe" filter), javascript: links, user HTML that must be shown (use a maintained sanitiser), server-built HTML strings.
    • 50–70 min: Content Security Policy: script-src, nonces, why 'unsafe-inline' removes most of the protection, report-only mode; a second layer, not the fix. Groups read three CSP headers and decide whether each would stop an injected inline script.
    • 70–85 min: Paper exercise: rewrite a vulnerable template so that each output is encoded for its context.
    • 85–90 min: Formative check.
  • TLA: Short lecture; group header reading; individual fix-on-paper exercise.
  • Materials and readings: OWASP Cheat Sheet Series (cross-site scripting prevention; Content Security Policy); Hoffman, Web Application Security (defending against cross-site scripting).
  • Formative check: Exit ticket: for a value placed inside an href attribute, which two checks are needed?
  • Homework: Read the CSP cheat sheet; prepare the lab 4 sheet. AI Level 2.

Week 5

Class 9 (Week 5, A): Credential stuffing, rate limiting and password-reset weaknesses

  • CLO (PO): CLO1 (PO1, PO2); CLO3 (PO3)
  • Contents and timing (90 min):
    • 0–5 min: Recap.
    • 5–25 min: Guessing, password spraying and credential stuffing: why passwords leaked from other sites work. Defences: rate limits per account and per source, the cost of account lockout, multi-factor authentication, checks against known-breached passwords. Password storage is a CSE-3651 topic; a two-minute reminder only.
    • 25–45 min: Designing a rate limit: what to count, over what window, what to return, where to enforce it (gateway or application). Worked example: one-time-password verification in an MFS app.
    • 45–70 min: Password-reset weaknesses: predictable or long-lived tokens, tokens leaked in links or logs, different messages that reveal which accounts exist, reset links built from an attacker-supplied host header, a reset that leaves old sessions alive. Groups review a reset flow diagram and find four flaws.
    • 70–85 min: Groups state the fixes as ASVS Level 1 style requirements ("the reset token expires within ..."); the teacher compares them with ASVS wording.
    • 85–90 min: Formative check.
  • TLA: Short lecture; worked example; group flow-diagram review; requirement writing.
  • Materials and readings: OWASP Cheat Sheet Series (authentication; forgot password); OWASP ASVS (authentication requirements at Level 1); Stuttard and Pinto, The Web Application Hacker's Handbook (attacking authentication).
  • Formative check: One-minute paper: one reset weakness and its fix.
  • Homework: Read the ASVS Level 1 authentication requirements and mark five that your semester-4 application did not meet. AI Level 2.

Class 10 (Week 5, B): Multi-factor authentication; OAuth 2.0 and OpenID Connect

  • CLO (PO): CLO1 (PO1, PO2); CLO3 (PO3)
  • Contents and timing (90 min):
    • 0–5 min: Recap.
    • 5–25 min: Multi-factor authentication and its bypasses: a one-time code not bound to the login session; the second step skipped by calling the next endpoint directly; unlimited code guesses; weak fallback channels; social engineering for codes; repeated push prompts.
    • 25–55 min: OAuth 2.0 authorisation-code flow with PKCE: the roles (resource owner, client, authorisation server, resource server) and the steps, drawn as a sequence on the board. OpenID Connect adds an ID token that says who logged in.
    • 55–75 min: Common mistakes: no state value; loose redirect_uri matching; tokens in URLs; treating an access token as proof of identity; not checking the ID token's issuer, audience, expiry and signature. Pairs read a short description of a "Login with ..." integration and list its mistakes.
    • 75–85 min: Link to ASVS Level 1 (CLO3): which requirements would have caught these mistakes?
    • 85–90 min: Formative check.
  • TLA: Board sequence diagram; pair case reading; whole-class mapping to ASVS.

4.2 Sessions

Rules for every session:

  • The exploit steps of each lab are on a department worksheet that names the local target and the page to use. This plan gives the aims, timing, fix, deliverable and checks; it does not repeat the worksheet steps.
  • Every target runs from a department image, on the student's own machine with ports bound to localhost only, or in the track range. A container published on all network interfaces would expose a vulnerable application to the lab network; the instructor checks the binding in labs 1 and 2 and spot-checks later.
  • The proxy's scope is set to the local target only. A separate browser profile is used for the lab and for nothing else.
  • Students work in pairs in weekly labs but each keeps an individual lab record page (T7) and writes their own two-sentence root-cause explanation.
  • Each weekly lab has three steps: exploit with guidance, explain the root cause in two sentences, fix and retest. Marks go to the explanation and the fix.
  • Bench sign-off: near the end of each session the instructor or teaching assistant asks each student to explain one item. A student who cannot explain an item gets "Not shown" for it under R1.

Lab 1 (Week 1): Set-up, interception and mapping; rules of engagement

  • Aims: Sign the rules of engagement before any lab work; run the local targets safely; capture and change a request with a proxy; map one target's attack surface.
  • Activities and timing (120 min):
    1. 0–20 min: Rules-of-engagement briefing (T1, schedule B): permitted targets, prohibited actions, data handling, the project's separate scope, the consequence of a breach. Questions; students sign. No one goes further without a signed agreement on file.
    2. 20–45 min: Start OWASP Juice Shop and DVWA from the department images, ports bound to localhost. Each student shows the instructor the port binding.
    3. 45–70 min: Set up Burp Suite Community Edition or ZAP with the lab browser profile; set the proxy scope to the local targets; capture a login request, change one harmless parameter (for example the language or page size) and observe the response.
    4. 70–100 min: Map Juice Shop by hand through the proxy. Record an attack-surface table: entry point, method, parameters, who can reach it, notes.
    5. 100–115 min: Bench sign-off: each student shows one captured and changed request and explains what changed.
    6. 115–120 min: Stop containers; complete the T7 record page.
  • Deliverable: Signed agreement; site map with attack-surface notes.

6.5 Sample questions with answers or marking notes

Remember (mid-term Q1 item, 1 mark). Name the three parts of a web origin. Answer: scheme, host, port. All three for the mark.

Understand (mid-term Q2 item, 3 marks). A developer says: "I use parameterised queries everywhere, so sorting by a column the user chooses is safe." Explain why this is wrong and what to do. Marking notes: placeholders carry values, not identifiers such as column names, so the column name is still joined into the query text (1); the user can therefore change the query's structure (1); fix with an allow-list that maps the user's choice to a fixed column name (1).

Apply (mid-term Q3a, 5 marks). The handler below lists a user's orders by status.

app.get('/orders', async (req, res) => {
  const status = req.query.status;
  const sql = "SELECT id, total FROM orders WHERE user_id = " + req.user.id +
              " AND status = '" + status + "'";
  res.json(await db.query(sql));
});

(a) Name the flaw and the line where data becomes code. (b) Describe in words what kind of status value would let a user see other users' orders, and why. (c) Write the fixed handler. Marking notes: (a) SQL injection; the line that joins status into sql (1). (b) A value that closes the quoted string and adds a condition that is always true, so the user_id restriction no longer limits the rows; the answer must explain the effect on the WHERE clause (2). (c) Placeholders for both values passed as parameters; optional allow-list check on status (2). A fix that only removes quote characters gets 0 for (c).

Analyse (mid-term Q4 item, 2 marks). User 12 is logged in. Request: GET /api/invoices/1043 with user 12's token. Response: 200 OK with an invoice whose customer_id is 57. Name the vulnerability class and the evidence. Answer: broken object-level authorisation (insecure direct object reference) (1); the evidence is that the returned invoice belongs to customer 57, not to the token's user, and the server answered 200 instead of 403 or 404 (1).

Create (mid-term Q5, 2 marks). Rewrite this finding: "XSS on site. Very dangerous. Please fix ASAP." Marking notes: a specific title with the class and component ("Stored cross-site scripting in product review comments"); steps to reproduce; impact in terms of what an attacker gains; severity with a reason; a fix by output context. One mark for title, component and steps; one for impact, severity and fix.

Analyse (final Q4a item, 7 marks). A scanner report lists eight findings for a supplied Node.js service with its code: (1) SQL injection at a line that uses a placeholder; (2) a hard-coded API key in a test fixture file; (3) a production configuration file containing a database password; (4) a vulnerable version of a library used only by the build tool; (5) a vulnerable version of the web framework, in the running service; (6) missing HttpOnly on the session cookie; (7) a weak hash function used to compute a cache key; (8) a cross-site scripting sink that receives only a constant string. Marking notes: real and ranked first: (3) secret in production configuration, (5) vulnerable framework in the running service, (6) session cookie without HttpOnly. Likely false positives with reasons: (1) parameterised, (7) the hash is not used for security, (8) no user input reaches it. Needs judgement: (2) test fixture key (real only if it is a live key), (4) build-time only, lower priority. One mark each for correct decisions with reasons on six items; one mark for a sensible ranking.

Create (final Q5, 7 marks). A school-management SaaS serves 40 schools from one database. Teachers, parents and school administrators log in. Design login, session handling and authorisation, and justify each choice against ASVS Level 1. Marking notes: login with rate limiting and a secure reset flow (1); multi-factor authentication at least for administrators (1); session cookie with Secure, HttpOnly, SameSite, rotation at login, idle and absolute time-outs (1); tenant taken from the verified session, never from the request (1); role and ownership checks in one central policy, deny by default (1); parents see only their own children's records, checked at object level (1); justification tied to named ASVS requirement areas (1).

Quiz item (Quiz 2, 3 marks). A reset link is https://.../reset?user=rahim&token=1700000123. Give two weaknesses and the fix for each. Marking notes: the token looks like a timestamp, so it is predictable (1); it is not bound to a random secret or may not expire (1); fix: a long random single-use token stored hashed with a short expiry, and old sessions ended after reset (1).

Quiz item (Quiz 4, 2 marks). Why can a chat application not rely on a system-prompt instruction such as "never reveal customer data"? Marking notes: the model treats the instruction and the attacker's text as the same kind of input, so a later instruction can override it (1); the real control is not giving the model access to data the user may not see (1).

Viva questions (R5) with what a good answer contains.

  1. Reproduce finding 3 from your report on the project target. (B) Done from the report's own steps, within about three minutes, with the evidence matching the report.
  2. Why does your patch remove the root cause and not just the example input? (C) Points to the changed line and says how data is now kept apart from code or how the check is now enforced on the server.
  3. What if the record IDs were long random strings instead of numbers: is the flaw gone? (D) No: random IDs make guessing harder but the missing ownership check is still the flaw; IDs leak in other places.
  4. Why did you rate this finding High and not Critical? (C) Names the CVSS metric that limits it, such as privileges required or the limited impact.
  5. During testing you found a password that works on a system outside your scope. What do you do? (E) Stop; do not use it; record it; report it to the instructor at once as the scope form requires.

6.9 CLO attainment: calculation and records

The method is README section 8.

  • Every question part, rubric criterion, test task and milestone above carries one CLO tag (the tables in 5.1–5.3 and 6.4–6.6).
  • A student's CLO score is the marks obtained on items tagged with that CLO divided by the maximum marks of those items. For attainment, all four quizzes count, not only the best three. Items missed with an approved absence are left out of both numerator and denominator.
  • A student attains a CLO at 50% (proposal). The course attains a CLO when at least 60% of the students who sat the final examination (theory) or the viva (lab) attain it (proposal).
  • Theory (CSE-4775) and lab (CSE-4776) are calculated and reported separately.
  • Record sheet (one per section): student ID; one column per tagged item; computed CLO1–CLO6 percentages for theory and for lab; attained yes or no; a class summary row.
  • Kept in the course file: question papers with CLO and Bloom tags and model answers; the two practical tests with variants and marking schemes; the project brief, scope forms and rubric; three marked samples (high, middle, low) of each examination, test, assignment and project report; the record sheet; the signed T1 register; a sample of T6 logs; the attainment report.
  • Closing the loop: any CLO below target gets a written cause and an action for the next offering (for example, CLO4 low: add a second triage exercise in week 11; CLO5 low: give the lab 13 worksheet a week early). The next teacher reads this report before week 1.

7. Support for weaker students

The intake is about 15% strong, 60% mid-level and 25% below average. Application security expects stronger programming than the rest of the track, so the course protects the floor carefully.

  • A small, clear floor. The minimum competency asks for one injection flaw and one access-control flaw, done properly, and one finding in standard form. Every weekly lab has a floor part (the guided exploit, the two-sentence root cause, one fix) and stretch parts. A student who completes the floor every week is on track to pass.
  • Guided first step. Each lab's exploit step is on a worksheet with the page and the expected evidence, so weaker students keep moving and spend their effort on the root cause and the fix.
  • Familiar code. All code is in JavaScript or TypeScript with SQL, the semester-4 studio language. A one-page reference sheet for Express handlers and database calls is given in week 2.
  • One-page sheets. HTTP request and response anatomy (week 1); output-encoding contexts (week 4); cookie and token settings (week 6); the T5 finding form (week 1); CVSS metrics in plain words (week 10). Students may bring their own A4 sheet into the practical tests.
  • Pairs with individual records. Weekly labs are done in pairs; each student keeps their own record and explains their own item at sign-off.
  • Practice before every Level 0 event. A practice variant of each practical test is released one week before (labs 6 and 11, last 15 minutes), and past quiz questions are discussed in class.
  • Early warning. After Quiz 1 (week 3) and Test 1 (week 7), students below 40% are invited to a one-hour clinic in the following week, run by the lab instructor or teaching assistant on the missed skill.
  • Project teams. The instructor mixes test-1 results in each team (section 5.3), and R7 requires each member to write and patch findings, so no one hides behind a stronger teammate.
  • Language. Discussion in labs may be in Bangla; findings and reports are in English. The teacher marks clarity of meaning, not grammar (R2 gives structure and English only 2 of 20).
  • SWE substitution students. A one-hour set-up clinic before week 1 and a buddy from the SEC track for the first two labs.
  • Strong students. Stretch goals from the outline: chain two low-severity findings into one high-impact attack on a lab target; write a custom Semgrep rule for a flaw class in their semester-4 code base, with test cases; run garak or promptfoo against the lab 13 application and compare with manual testing.

9. Issues for the committee

  1. Week 14 does not fit in one 2-hour lab. About 12 team readouts plus about 30 individual vivas with live reproduction need roughly 6 examiner-hours. The plan uses the lab slot for readouts and an extra slot with two examiners for vivas. The committee should approve the extra slot and the second examiner.
  2. The department-built targets are a standing workload. The outline requires two unseen targets (tests with variants, and the project with at least six flaw classes). They take weeks to build, leak once students have them, and should be refreshed each year. The committee should name who builds and maintains them and give time for it.
  3. Overlap with CSE-3652. CSE-3652 weeks 8–9 already use Juice Shop or DVWA for SQL injection, command injection, path traversal, cross-site scripting, request forgery and access control. CSE-4776 labs 2–4 return to the same targets, and students may already know the public walkthroughs. A decision is needed: accept the overlap, or ask the two courses to use different practice targets or levels.
  4. CVSS version. The outline says "severity with CVSS" without a version. The examples use version 3.1. The department should fix one version for the whole track (CSE-3675 also uses CVSS).
  5. Lab 13 resources. A local model in Ollama plus the chat application and a browser may not run well on 8 GB lab PCs. The alternative, the CSE-3660 model access, has a cost and the provider's terms on adversarial testing must be checked. The committee should decide which to use and who checks the terms.
  6. Identifying SWE substitution students early. The outline asks for the range guide and rules of engagement a week before week 1, but there is no stated step that tells the teacher who these students are before registration closes. The registration office should send the list.
  7. The 30/50 split of written marks is a working assumption until the university regulation is confirmed (framework section 17, item 6).

Appendix A: Project scope and test plan form

1. Parties. Team members (names, IDs); instructor (acting as the application owner's representative).

2. Target. Application name and image version given by the department; image checksum; where it will run (localhost on named machines, or lab PCs); nothing else is in scope.

3. Testing window. Start and end dates (weeks 10–13); hours.

4. Accounts. The test accounts supplied and their roles. No other accounts are created except through the application's own sign-up, if the brief allows it.

5. In scope. The application's web pages and API on the local instance.

6. Out of scope. Denial of service and load testing; the host operating system and Docker itself; any other address or machine; social engineering; anything not listed in 5.

7. Stop conditions. Stop and tell the instructor at once if: the target behaves as if it is not the local instance; you find credentials or data that point to a real system; you find you have tested anything outside section 5.

8. Data handling. Evidence stays in the team repository. The image and its code are not shared, uploaded or pasted into an outside AI service. The image is deleted after the viva and deletion is confirmed below.

9. Test plan. Table: WSTG category; tests chosen; time box; team member; status (planned, done, not done and why).

10. Signatures. Each team member and the instructor, with date. Image released only after all signatures.

11. Deletion confirmation. Each member signs after the viva: "I have deleted the project image and all copies."

Appendix B: Penetration-test report structure

  1. Management summary (one page). What was tested and when; overall risk in plain words; the three most important findings and actions.
  2. Scope and method. From Appendix A; the test plan's coverage and what was not tested.
  3. Findings. One T5 entry per finding, ordered by severity: title; affected component; steps to reproduce; impact; severity with CVSS vector and reasons; evidence (request and response, screenshots, UTC times); recommended fix; retest result.
  4. Patches. The two patches as diffs, with retest evidence.
  5. Appendix. Evidence log; T6 AI-use log and disclosure statement; each member's contribution statement (R7).
