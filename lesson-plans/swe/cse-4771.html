1. Course facts

Copied from the outline without change.

Codes and titlesCSE-4771 Full-Stack & Mobile Application Engineering (theory); CSE-4772 Full-Stack & Mobile Application Engineering Lab
Credits and contactTheory 3 cr, 3 h/week; Lab 1 cr, 2 h/week
SemesterS7
CategoryTrack SWE (Track Course II)
PrerequisitesCSE-2325 Object-Oriented Programming & Design; CSE-2423 Database Systems; CSE-2434 Software Engineering Studio; CSE-3651 Information Security; a pass in CSE-2440 Core Competency Assessment. SWE students have also taken CSE-3671
AI-use levelExaminations and quizzes: 0. Assignments: 2. Lab work: 2, except weeks 1–2 (Level 1). Lab project: 2. Lab tests and viva: 0.

Course learning outcomes

CLOOn completing the course the student canBloomPO
1Build a typed web client from components, with state held in the right place, routing, validated forms, and loading, empty and error statesApplyPO3, PO5
2Design and implement a back-end service in a statically typed framework: validated API, layered structure, persistence with migrations, transactions and a uniform error formatCreatePO3
3Implement authentication and authorisation correctly: session or token handling, OpenID Connect sign-in, and role and ownership checks enforced on the serverApplyPO3, PO5
4Add real-time updates and background work, and analyse how client cache and server state can disagreeAnalysePO2, PO3
5Build a cross-platform mobile client that shares the API contract with the web client and behaves sensibly on a poor connectionApplyPO3, PO5
6Measure accessibility and performance against stated targets, and review framework-generated and AI-generated code for defects in both and in access controlEvaluatePO4, PO5

Minimum competency (from the outline)

Every passing student can, unaided:

  • From a given API contract, build a React and TypeScript screen that lists, creates and edits a resource, with loading, empty and error states and no use of any.
  • Add an endpoint to an existing Spring Boot service: controller, validation, service, repository and migration, with correct status codes and one test.
  • Protect an endpoint so that users can read and change only their own records, and prove it with a request that is refused.
  • Say where their application keeps the session or token, how it is sent, when it expires, and what an attacker gains by stealing it.
  • Run an automated accessibility check and a keyboard-only walk-through of a page, and fix the label, contrast and focus problems found.

Stretch goals (from the outline)

  • An offline-first mobile client with a local store, background sync and a stated rule for conflicts.
  • Server-side rendering of one public page with Next.js, with the change in Largest Contentful Paint measured.
  • An Android build produced and distributed by the CI pipeline, with the client's types generated from the OpenAPI contract at build time.

The stack (fixed per section, from the outline)

  • Web client: TypeScript and React, built with Vite; TanStack Query, React Router, Zod; ESLint and Prettier.
  • Server: Java on a current long-term-support JDK, Spring Boot, Spring Data JPA, Flyway, PostgreSQL; Keycloak as the identity provider; Docker for local services.
  • Mobile: React Native with Expo, run on phones through Expo Go.
  • A department that prefers C# with ASP.NET Core on the server can use it without changing the weekly plan. The class and lab plans below name Spring Boot; the same steps apply.

2. Class pattern (assumption to confirm)

These are the README assumptions A1–A8, applied to this course.

  • Theory: 3 contact hours a week, given as two 90-minute classes (Class A and Class B). That makes 28 classes in 14 teaching weeks.
  • Lab: one 2-hour session a week, 14 sessions. Where the timetable allows, the lab falls after the week's two theory classes.
  • Examinations: the mid-term (weeks 1–7) is held in a mid-semester examination week after week 7. The final (whole course) is held after week 14. Neither is inside the 14 teaching weeks.
  • Quizzes: three Level 0 code-reading quizzes of 15 minutes each, at the start of a class:
    • Quiz 1 in Class 7 (week 4), on weeks 1–3;
    • Quiz 2 in Class 17 (week 9), on weeks 5–8;
    • Quiz 3 in Class 23 (week 12), on weeks 9–11.
  • Theory assignment: released in Class 22 (week 11), due at the end of week 13, discussed in Class 27 (week 14).
  • Project demonstrations: held in an extra 2-hour slot in the examination period. The week-14 lab session is used for the individual vivas (see 6.7 and README issue T1).
  • Re-split: if the department uses three 60-minute classes, keep each week's content and order. Break each 90-minute plan at its main activity, and move the formative check to the end of each 60-minute class. A quiz stays at the start of the first class of its week.

3. Theory lesson plan

Each week's two classes cover that week's outline topics in the outline's order. Times in each class add up to 90 minutes. Homework is unmarked practice (README A9); try it unaided first, because quizzes and examinations are Level 0.

Week 1 — From the studio to an industrial stack; TypeScript; the Level 2 working agreement

Class 1 — Week 1: What frameworks give and hide; TypeScript in strict mode

  • CLO / PO: CLO 1 (PO3, PO5)
  • Contents and timing (90 min):
    • 0–10 min: Course map. This course is the "build" step of the track: design (CSE-3671), build (this course), verify (CSE-4781), operate (CSE-4881). Walk through the assessment calendar (section 6.2) and the AI-use table (README 4.1).
    • 10–30 min: From the semester-4 studio to an industrial stack. Students list what they wrote by hand in CSE-2434: routing, data access, session handling, validation, JSON parsing. The teacher writes next to each item the framework piece that will do it in this course: React Router, TanStack Query, Spring MVC, Spring Data JPA, Spring Security. Then: what each piece hides. Examples: the SQL that JPA writes, the filter chain that Spring Security runs, the re-renders that React performs.
    • 30–55 min: TypeScript for application code. Why static types on both sides of the API. tsconfig.json in strict mode: strict, noImplicitAny, strictNullChecks. Live coding: a JavaScript function that fails at run time with "cannot read properties of undefined" becomes a compile error in strict TypeScript.
    • 55–75 min: Types for data: object types, type aliases and interfaces, optional and readonly properties, arrays, literal types. Worked example: type a Patient record from a printed JSON sample, including a field that can be null.
    • 75–85 min: Formative check.
    • 85–90 min: Homework and preview of Class 2.
  • TLA: Think-pair-share on "what did the studio make you write by hand?". Short lecture. Live coding in which the class predicts each compiler error before the teacher runs the checker.
  • Materials: Boris Cherny, Programming TypeScript (chapters on the type system and on types). TypeScript official documentation (handbook; compiler options for strict mode). Visual Studio Code.
  • Formative check: Three short snippets on the board. For each, students write "accepted" or "rejected under strict mode" and one reason. Show of hands; the teacher notes which snippet most students got wrong and returns to it in Class 2.
  • Homework (Level 2, unmarked): Write TypeScript types for five printed JSON samples: patient, appointment, doctor, error response, and a paginated list of appointments. Mark which fields may be missing or null.

Class 2 — Week 1: Unions, narrowing, generics; types as the contract; the Level 2 working agreement

  • CLO / PO: CLO 1 (PO3, PO5)
  • Contents and timing (90 min):
    • 0–5 min: Recap: the snippet most students got wrong in Class 1.
    • 5–30 min: Union types and discriminated unions. Narrowing with typeof, in, and a check on a kind field. Exhaustive checks with never. Worked example: type LoadResult = { kind: "ok"; data: Patient } | { kind: "notFound" } | { kind: "error"; message: string } and a switch that the compiler checks.
    • 30–45 min: Generics: Page<T>, ApiResult<T>, a generic fetchJson<T> helper; constraints with extends. Faded example: the teacher writes Page<T>; students write a function that returns the first item of a Page<T> or undefined.
    • 45–60 min: unknown against any. Data from the network is unknown until it is checked. any switches the checker off and spreads. The course rule: no any in submitted code; the linter enforces it.
    • 60–70 min: Types as the contract between client and server. One source of truth: the OpenAPI contract (week 4), from which client types are generated. What happens to the client when the server renames a field, with and without generated types.
    • 70–82 min: The Level 2 working agreement for this course. Usage log (README template 6.2). Every piece of AI output is tested before it is committed. Every line can be defended in the viva. Lab weeks 1–2 are Level 1: AI may explain errors but may not write code. Show one good and one poor log entry and ask which would satisfy an examiner.
    • 82–90 min: Formative check and homework.
  • TLA: Worked example, then faded example. Pair exercise. Comparison of two log entries.
  • Materials: Dan Vanderkam, Effective TypeScript (items on unions and on preferring unknown to any). Cherny, Programming TypeScript (chapter on generics). README section 4 and template 6.2.
  • Formative check: Each student writes a type LoginResult for a sign-in call that succeeds with a user name and an expiry time, or fails as "wrong password" or "account locked". A partner checks that code using it must narrow before reading the user name.
  • Homework (Level 2, unmarked): Read the items on any and unknown in Effective TypeScript. Convert a supplied JavaScript getJson(url) helper to return Promise<unknown>, and write a narrowing function that turns it into Patient[] or throws.

Week 2 — React's component model

Class 3 — Week 2: Props, state and rendering; effects and their pitfalls

  • CLO / PO: CLO 1 (PO3, PO5)
  • Contents and timing (90 min):
    • 0–10 min: Warm-up: one narrowing question from week 1, answered on paper and checked by a neighbour.
    • 10–30 min: The component model. A component is a function from props and state to UI. JSX. Props are read-only. useState. A state change re-renders that component and its children. Live coding: a counter, then a PatientCard list built from a typed array.
    • 30–45 min: Rendering and re-rendering. When React re-renders. Why items.push(x) followed by setItems(items) does not update the screen. Immutable updates with spread syntax. Predict-then-run: students predict the screen after each click before the teacher runs it.
    • 45–70 min: Effects. What useEffect is for: keeping a component in step with something outside React (a timer, a subscription, a network request). The dependency array. Cleanup functions. Pitfalls: stale closures, missing dependencies, an effect that sets state and triggers itself, and two fetches that return in the wrong order. Code-reading exercise: four printed effects; pairs mark each as correct or faulty and name the fault.
    • 70–82 min: Formative check.
    • 82–90 min: Homework; preview of Class 4.
  • TLA: Live coding with predictions. Code-reading exercise in pairs. Short lecture.
  • Materials: React official documentation (sections on describing the UI, adding interactivity, state as a snapshot, and synchronising with effects). MDN Web Docs on JavaScript closures.
  • Formative check: A component starts a 1-second interval in an effect with an empty dependency array and calls setCount(count + 1). What does it show after three seconds, and why? (Answer: 1; the closure keeps count as 0. Fix: setCount(c => c + 1).)
  • Homework (Level 2, unmarked): Three predict-the-output exercises on re-rendering and effects from the course sheet. Write the prediction first, then run the code and explain any difference in two sentences.

Class 4 — Week 2: Lists and keys, controlled forms, composition, and who owns the state

  • CLO / PO: CLO 1 (PO3, PO5)
  • Contents and timing (90 min):
    • 0–5 min: Recap of the stale-closure answer.
    • 5–25 min: Lists and keys. Why React needs keys. Live demonstration: a list of rows, each with a text input; using the array index as the key, delete the first row and watch the typed text move to the wrong row. Fix with a stable id.
    • 25–45 min: Controlled forms. value and onChange. Showing validation messages. Submit handling. Disabling the button while a request is in flight. A <label> for every input from the start (week 11 returns to this).
    • 45–60 min: Composition. Small components, children, lifting state up to a common parent, passing callbacks down.
    • 60–80 min: Deciding which component owns a piece of state. Rule: the closest common parent of the components that need it. Values that can be computed from other values are not state. Design critique: groups of three receive a printed component tree with state in the wrong places, move each piece of state, and say why.
    • 80–90 min: Formative check and homework.
  • TLA: Demonstration of the key bug. Design critique in groups of three. Short lecture.
  • Materials: React official documentation (rendering lists; reacting to input with state; choosing the state structure; sharing state between components).
  • Formative check: Given a tree of SearchPage, SearchBox, FilterPanel and ResultList, each student writes which component owns query, filters and results, and names one value that should be derived rather than stored.
  • Homework (Level 2, unmarked): Refactor a supplied form component that stores fullName as well as firstName and lastName. Remove the derived state and keep the form working.

Week 3 — Client state and server state

Class 5 — Week 3: Client and server state; the URL as state; the query cache

  • CLO / PO: CLO 1 (PO3, PO5); CLO 4 (PO2, PO3)
  • Contents and timing (90 min):
    • 0–5 min: Recap question on state ownership.
    • 5–25 min: Two kinds of state. Client state belongs to the screen: whether a dialog is open, what is typed in a field. Server state belongs to the server; the client holds a copy that can be out of date. Why keeping server data in useState with hand-written fetching causes stale lists, duplicate requests and lost errors. The class builds a two-column comparison table.
    • 25–45 min: Routing and the URL as state. React Router: routes, path parameters, nested routes, links. Search parameters for filters and the page number. A filter held in the URL survives a reload and can be sent to a colleague; a filter held in useState cannot. Live coding: /appointments?status=open&page=2.
    • 45–75 min: Data fetching with a query cache (TanStack Query). Query keys. useQuery. Caching and stale time. Background refetch. Invalidation after a change. Live coding: replace the hand-written fetch plus useEffect from week 2 with useQuery, then list what disappeared from the code (loading flags, race handling) and what the library now does without being asked (retries, refetch when the window regains focus).
    • 75–85 min: Formative check.
    • 85–90 min: Homework.
  • TLA: Comparison table built with the class. Live coding. Pair discussion: "what does the library now hide from you?"
  • Materials: React Router and TanStack Query (tools named in the outline; their own documentation). React official documentation. Vanderkam, Effective TypeScript (items on typing data from outside the program).
  • Formative check: Students classify eight pieces of state (search text, selected tab, list of appointments, current page number, logged-in user's profile, whether a menu is open, unsaved form input, list of doctors) as client state, server state or URL state, with one reason each.
  • Homework (Level 2, unmarked): For a list page with two filters and a page number, write the query keys you would use and the cases in which each key's data must be invalidated.

Class 6 — Week 3: Pagination and optimistic updates; schema validation; loading, empty and error states

  • CLO / PO: CLO 1 (PO3, PO5); CLO 4 (PO2, PO3)
  • Contents and timing (90 min):
    • 0–5 min: Recap: one query-key question from the homework.
    • 5–25 min: Pagination with a query cache. Page-and-size against cursor pagination. Keeping the previous page on screen while the next one loads. The page number as part of the query key.
    • 25–45 min: Optimistic updates. Change the cache first, send the request, roll back on error. Worked example on a timeline drawn on the board: what the user sees, what the cache holds, what the server holds, at each step. When not to be optimistic: payments, and any action the user cannot easily undo.
    • 45–65 min: Schema validation of forms with Zod. One schema gives both a run-time check and a TypeScript type (z.infer). Validating network responses too: from unknown to a typed value. The server must still validate; client validation is for the user's convenience, not for security.
    • 65–80 min: Loading, empty and error states as requirements. Write them as acceptance criteria. Design critique of three printed screenshots: a blank screen while loading, the word "undefined" in a table, a spinner that never stops after a network error.
    • 80–90 min: Formative check and homework.
  • TLA: Timeline worked example. Design critique. Short lecture.
  • Materials: TanStack Query and Zod (tools named in the outline; their own documentation). Vanderkam, Effective TypeScript (items on the difference between compile-time types and run-time values).
  • Formative check: Each student writes three acceptance criteria in given–when–then form for a "My appointments" page: one each for loading, empty and error.
  • Homework (Level 2, unmarked): Write a Zod schema for an appointment form: patient name (2–60 characters), Bangladeshi mobile number (11 digits starting with 01), date not in the past, and an optional note of at most 200 characters. Derive the TypeScript type from it.

Week 4 — Back end I with Spring Boot

Class 7 — Week 4: Quiz 1; dependency injection; controllers and request validation

  • CLO / PO: CLO 2 (PO3). Quiz 1 assesses CLO 1.
  • Contents and timing (90 min):
    • 0–15 min: Quiz 1 (Level 0, 15 minutes, code reading on weeks 1–3; see 6.4).
    • 15–25 min: What the framework now does that students did by hand in CSE-2434: request parsing, routing, JSON conversion, validation, database connections. Students match five fragments of their studio code to the Spring feature that replaces each.
    • 25–45 min: Dependency injection. Beans, constructor injection, the application context, component scanning. Why injection makes classes easy to test and keeps dependency direction clean (link to CSE-3671 modularity). Live demonstration: a controller, a service and a repository wired by Spring.
    • 45–70 min: Controllers. @RestController, request mappings, path variables, query parameters, request bodies, response status. Request validation with Jakarta Bean Validation: @Valid, @NotBlank, @Size, @Pattern. What Spring returns by default when validation fails, and why that default is not good enough for a client.
    • 70–82 min: Code-reading exercise (also the formative check).
    • 82–90 min: Homework.
  • TLA: Quiz. Matching exercise. Live coding. Code reading in pairs.
  • Materials: Craig Walls, Spring in Action (chapters on getting started with Spring and on writing REST services). Spring Boot official documentation.
  • Formative check: Given a printed controller with validation annotations, students predict the HTTP status and body for three requests: a valid one, one with a missing field, and one with a string where a number is expected.
  • Homework (Level 2, unmarked): Read the dependency-injection material in Spring in Action. Draw the object graph that Spring builds for a three-class example and mark which class could be replaced by a fake in a test.

Class 8 — Week 4: DTOs and entities; exception handling and one error format; configuration; OpenAPI from code

  • CLO / PO: CLO 2 (PO3)
  • Contents and timing (90 min):
    • 0–5 min: Quiz 1 returned with a model answer; the most common error discussed.
    • 5–25 min: DTOs against entities. Why an API should not return entities: it leaks fields (a password hash, internal flags), it causes lazy-loading errors, and it ties the API to the table design. Mapping between them. Java records as DTOs.
    • 25–45 min: Exception handling and one error format. @RestControllerAdvice. Mapping exceptions to status codes. One error body for the whole API, using Spring's problem-details support. Worked example: 400 with a list of field errors, 404, 409.
    • 45–60 min: Configuration and profiles. application.yml, environment variables, dev, test and prod profiles. Secrets never go into Git.
    • 60–78 min: OpenAPI generated from code. The contract file that the build produces. Generating TypeScript types for the client from that file. Contract drift: how a check in the pipeline catches a server change that would break the client.
    • 78–90 min: Formative check and homework.
  • TLA: Short lecture with a worked example. Live demonstration of contract generation. Pair work on the formative task.
  • Materials: Walls, Spring in Action (REST chapters). Spring Boot official documentation. OWASP Cheat Sheet Series (error handling).
  • Formative check: Given an entity User with passwordHash, roles and failedLoginCount, each student writes the DTO for GET /api/me and the error body for a request with two invalid fields.
  • Homework (Level 2, unmarked): Write a half-page "error format" section for an API style guide: status codes used, the body shape, and two examples.

Week 5 — Back end II, persistence

Class 9 — Week 5: Mapping with JPA; lazy loading and the N+1 problem

  • CLO / PO: CLO 2 (PO3)
  • Contents and timing (90 min):
    • 0–5 min: Recap question on DTOs.
    • 5–30 min: Mapping with JPA. Entities, identifiers, relationships (@ManyToOne, @OneToMany), the owning side, cascade rules. Spring Data repositories and derived query methods.
    • 30–60 min: Lazy loading and the N+1 problem. Live demonstration with SQL logging switched on: list 20 orders and print the item count of each; the log shows 21 queries. Diagnose from the log. Fixes: a fetch join, @EntityGraph, or a DTO projection. The cost of each fix (loading too much, duplicated rows, more code).
    • 60–78 min: Code-reading exercise. Four printed service methods; pairs count the SQL queries each one runs for 50 rows and choose a fix.
    • 78–90 min: Formative check and homework.
  • TLA: Live demonstration with the SQL log on the projector. Code reading in pairs. Short lecture.
  • Materials: Walls, Spring in Action (chapter on working with data and Spring Data JPA). Spring Boot official documentation. PostgreSQL.
  • Formative check: A loop over 50 customers calls customer.getOrders().size(). How many queries run? Write the repository method that fixes it.
  • Homework (Level 2, unmarked): Switch on SQL logging in the starter project and record the number of queries for each list page. Note any page with more than three queries.

Class 10 — Week 5: Transactions and isolation; lost updates and optimistic locking; migrations; when to write SQL

  • CLO / PO: CLO 2 (PO3)
  • Contents and timing (90 min):
    • 0–5 min: Recap: the N+1 fix from Class 9.
    • 5–25 min: Transactions in practice. @Transactional on service methods. Rollback rules for checked and unchecked exceptions. The self-invocation pitfall: a transactional method called from the same class runs without a transaction.
    • 25–40 min: Isolation in practice (from CSE-2423). PostgreSQL's default level, Read Committed. Which anomalies it still allows.
    • 40–60 min: Lost updates. Worked example on a timeline: two staff members edit the same appointment; the second save silently overwrites the first. Optimistic locking with @Version; returning 409 Conflict; what the client should show. When a pessimistic lock is the better choice.
    • 60–75 min: Schema migrations with Flyway. Versioned scripts. Never edit a migration that has already run. Migrations run in the pipeline. A preview of expand and contract (from CSE-3671).
    • 75–82 min: When to write SQL directly: reports, bulk updates, queries JPA expresses badly. Native queries and JdbcTemplate.
    • 82–90 min: Formative check and homework.
  • TLA: Timeline worked example on the board. Think-pair-share on "which save wins?". Short lecture.
  • Materials: Walls, Spring in Action (data chapters). Spring Boot and Flyway documentation. PostgreSQL documentation on transaction isolation.
  • Formative check: A timeline shows two edits of one record. Students write what is saved without a version column, and what the second user sees with one.
  • Homework (Level 2, unmarked): Write two Flyway migrations for the starter schema: add a nullable column, then fill it and make it required. Explain why it is done in two steps.

Week 6 — Authentication

Class 11 — Week 6: Sessions against tokens; cookie attributes; JSON Web Tokens

  • CLO / PO: CLO 3 (PO3, PO5)
  • Contents and timing (90 min):
    • 0–5 min: Recap question on optimistic locking.
    • 5–25 min: Authentication recap from CSE-3651. Server sessions: a session id in a cookie, state on the server. Tokens: a signed, self-contained value checked without a lookup. The class builds a trade-off table: revocation, scaling, mobile clients, cross-domain use.
    • 25–45 min: Cookie attributes: HttpOnly, Secure, SameSite (Strict, Lax, None), Path, Max-Age. Demonstration in the browser's developer tools. What a cross-site scripting attack can and cannot read.
    • 45–70 min: JSON Web Tokens. Header, payload and signature. Verification: signature, issuer, audience, expiry. Access tokens and refresh tokens. The revocation problem: a stolen token works until it expires. Where a browser application can keep a token (memory, local storage, a cookie) and what each choice exposes.
    • 70–82 min: Case discussion. Three products: a coaching-centre manager served from one domain; a public API used by a partner's server; a mobile app. Groups choose sessions or tokens for each and give two reasons.
    • 82–90 min: Formative check and homework.
  • TLA: Trade-off table built with the class. Demonstration in developer tools. Case discussion in groups.
  • Materials: Laurențiu Spilcă, Spring Security in Action (chapters on authentication). OWASP Cheat Sheet Series (session management; JSON Web Tokens). MDN Web Docs on HTTP cookies.
  • Formative check: A decoded JWT payload is printed. Students answer: who is the user, when does the token expire, which roles does it claim, and may the server trust these claims without checking the signature?
  • Homework (Level 2, unmarked): Write a half-page answer: "Where does my studio application keep its session or token, how is it sent, when does it expire, and what does an attacker gain by stealing it?" (This is a minimum competency.)

Class 12 — Week 6: OAuth 2.0 and OpenID Connect with PKCE; using an identity provider

  • CLO / PO: CLO 3 (PO3, PO5)
  • Contents and timing (90 min):
    • 0–5 min: Recap: one answer from the homework read out and discussed.
    • 5–20 min: Why not write your own sign-in. Password storage, reset, multi-factor sign-in and lock-out are hard to get right; an identity provider does them. Keycloak as the local identity provider. The roles: user, client application, authorisation server, resource server (the API).
    • 20–50 min: The authorisation-code flow with PKCE, step by step. 4. Lab lesson plan

How the lab works (from the outline):

  • Weeks 1–6 are individual guided labs that grow one small application slice by slice. The team project runs from week 6 to week 14.
  • By hand first. In weeks 1–2, types, fetching and state are written without AI-written code and without a data library (Level 1). From week 3, libraries and AI at Level 2 take over.
  • Lab PCs are short of memory for an Android emulator beside an IDE and containers. Mobile labs therefore run on students' own Android phones through Expo Go. Three or four low-cost Android phones are kept in the lab for students without one.
  • The starter repository builds offline on lab machines, from a local mirror of the npm and Maven dependencies and a local cache of the Docker images (PostgreSQL, Keycloak).
  • Every session has a catch-up branch, published the day after the session, so that a student who missed or failed one session can start the next (README section 10).

What is supplied. A repository of the course sample application at a fixed commit, and one open pull request titled "Clinic queue: patients can see and cancel their own tokens; reception calls the next token". Before the semester, the theory teacher produces this pull request with an AI assistant, then keeps or plants about eight defects. They are of these kinds:

  • Access control. The cancel endpoint has no ownership check. The "call next token" endpoint is protected only by hiding the button for non-reception users.
  • Data. The token number is assigned by reading the current maximum and adding one, without a transaction or a unique constraint, so two patients can get the same number.
  • Performance. The queue list runs one query per token to fetch the patient name. The list endpoint has no maximum page size.
  • Client. The list is not invalidated after a cancel, so it shows stale data. One screen has no error state.
  • Accessibility. "Cancel" is a clickable div. A token's status is shown by colour only.
  • Library. One configuration call that does not exist in the course's Spring Security version.
  • Tests. One test asserts the wrong behaviour, so it passes on the defect.

Two variants (A and B) are issued by roll-number parity. They differ in where the defects are placed. The list of defects is kept confidential and filed in the course file after marking.

Task.

  1. Read the pull request description and the diff. Run the application at the pull-request commit.
  2. Find defects. For each one, write a review comment in the format of README template 6.3, with:
    • the file and line;
    • the label (blocking, suggestion or question);
    • what goes wrong for a user or for the client;
    • evidence: a request that succeeds but must be refused (saved as a request file or a command with its output), a failing test, a screenshot, or an extract of the SQL log;
    • the fix you propose, in code or in clear words.
  3. Rank your five most serious findings by risk to users and the client, with one sentence each.
  4. Write a short paragraph, "What the assistant got wrong". If you used an assistant, list the findings it missed and any it invented. If you did not use one, write "AI use: Level 2 permitted; none used".
  5. End with a verdict: approve, or request changes, with one paragraph of reasons.

Rules.

  • A finding without evidence earns at most half of the marks it would otherwise earn.
  • A correct piece of code marked as a blocking defect costs 0.5 mark from the "severity, ranking and fixes" criterion (at most 1 mark in total).
  • Put the disclosure line from README template 6.2 at the top of the document.
  • Fixing the code is not required. A patch branch may be added but is not marked.

Marking notes (8).

  • Ownership (CLO 3, 4 marks).
    • cancel never checks who owns the order. Any signed-in user can cancel any order whose id they know or guess. (1 for naming it, 1 for the consequence.)
    • Fix: pass the subject from the token into the service, and load the order with findByIdAndCustomerId(id, subject), returning 404 when nothing is found. (2)

Kind 5 — Case: mobile sync for field workers (CLO 5; 8 marks)

An NGO has 40 field workers who record household health surveys in villages with weak mobile data. A worker may be offline for two days. A supervisor sometimes corrects a survey on the web while the worker is still offline. Design the sync behaviour of the React Native client. Cover storage, sending, conflicts, sign-in and what the worker sees.

Marking notes: 1 mark per point, up to 8.

  1. Local store on the device (SQLite) for surveys and drafts.
  2. Outbox queue with a client-generated id for each survey and each change.
  3. Idempotent server endpoints, so that a replay does not duplicate a survey.
  4. Sync on reconnect, on app resume and by a manual button, with backoff.
  5. A conflict rule stated for edited records. Example: each record carries a version; a stale version gets 409; the supervisor's correction wins for verified fields, and the worker sees a conflict list. New surveys are append-only and do not conflict.
  6. Tokens in secure storage. The refresh-token lifetime covers the offline period, or the queue is kept and sign-in is asked for at sync without losing data.
  7. The worker sees sync status per record and the last sync time.
  8. Personal data on the device is kept to a minimum and protected.

A design with no stated conflict rule earns at most 5.

6.9 CLO attainment: how it is computed and recorded

The method is README section 7. For this course:

  1. Theory sheet. One column per assessed item, with its CLO tag and maximum marks:
    • mid-term Q1–Q5b (Q4 split into two columns, CLO 2 and CLO 3);
    • final Q1–Q8b (Q3 split into two columns);
    • the three quizzes, entered as their weighted marks and split by CLO as in 6.8;
    • the five assignment criteria.
  2. Lab sheet. One column per item:
    • the six check-off groups and the two record checks;
    • PT1 tasks 1–3;
    • PT2 "D1", "second defect" and "third defect" (tagged CLO 3, CLO 6 and CLO 6, whichever defects the student chose);
    • project criteria T1–T7 (entered after the contribution factor) and I1–I4;
    • viva criteria A–D, with A and B split by CLO as in 6.7.
  3. Student and class attainment. A student attains a CLO with at least 50% of the marks tagged to it. The class attains it when at least 60% of the students who completed the course attain it. Both thresholds are proposals (README A12).
  4. Students who fail the viva gate. Their marks still go into the sheet as awarded. The attainment figures report what was shown, not the grade.
  5. Recording. The theory teacher and the lab instructor complete their sheets within two weeks of results and file them in the course file (README 8.1).
  6. Course report. It gives the six attainment figures for each sheet. For any CLO below target it gives one cause and one change for the next offering. CLO 4 has the fewest theory marks (7), so its figure rests on few items. If it is below target, check the final Q5 scripts before changing the teaching.

7. Support for weaker students

The intake is about 15% strong, 60% mid-level and 25% below average (README section 10). The outline warns that the stack is broad and weaker students drown in tooling. These measures extend the outline's instructor notes.

  1. One stack, offline. One fixed stack per section. A starter repository that builds offline on lab machines from mirrored npm and Maven dependencies and cached Docker images. No student loses a session to downloads.
  2. Individual weeks with a weekly check-off. Weeks 1–6 are individual, with a check-off every week. A student who scores 0 or 1 in two sessions in a row is invited to the weekly clinic before the next session.
  3. The minimum competencies as drills. Each of the five minimum competencies is practised twice before the test that checks it:
    • typed screen: Sessions 2 and 3, before practical test 1;
    • endpoint: Sessions 4 and 5;
    • ownership check with a refused request: Session 6 and the Class 13 matrix exercise;
    • "where is my token": Class 11 homework and Session 6;
    • accessibility fixes: Classes 21 and 22 and Session 11, before practical test 2.
  4. Practice tests. A third version of each practical test, with its marking scheme, is released one week before the test (weeks 6 and 12). Students do it as homework, unaided.
  5. A stack map. A one-page diagram of one request through the stack: React component, query hook, HTTP request, controller, service, repository, table. It names the matching file in the starter. It is given out in week 4 and used in every check-off question.
  6. An error-message phrasebook. The lab instructor collects the error messages most often met in the pilot run of the labs (TypeScript, Spring, Flyway, Keycloak, Expo). For each, it gives the meaning in plain English and the first thing to try. It is updated each week from the check-off notes.
  7. An unhappy-path checklist. Used in every check-off from week 3: refused request, empty list, server error, two users editing, no network. This makes visible the parts that students and assistants both skip.
  8. Balanced teams and fair slices. The instructor forms project teams with mixed levels. A weaker student owns a simpler slice (for example, list, create and edit with an ownership check) that still runs from screen to table. They do not own the real-time or offline part alone.
  9. Phones. The three or four lab phones are lent out during mobile sessions. Students without a phone pair with one who has. The instructor's connection checklist for Expo Go is printed and posted in the lab.
  10. Explain before commit. At Level 2, weaker students tend to accept generated code they cannot read. Each pull request lists, in its description, any block written by an assistant with one line on what it does. Check-off questions are often about those blocks. This also prepares students for the viva.
  11. Clinics and early warning. One optional clinic hour a week. A focused clinic on the minimum competencies in weeks 6 and 12. After practical test 1 and the mid-term, students below 40% in either get a 30-minute meeting and a written plan of two or three tasks (README section 10).
  12. Language. A one-page glossary with a short Bangla gloss for terms that confuse: state, cache, stale, idempotent, ownership, migration, token, contrast. Discussion in Bangla is welcome. Written work is in English and is judged by README 5.5, not by grammar.
  13. Stretch work for the strongest students. The outline's stretch goals, optional and without extra marks: an offline-first client with background sync; server-side rendering of one public page with Next.js, measured; an Android build from the pipeline with types generated at build time.

9.2 Expo Go on the campus network.

  • Expo Go on a phone must reach the development server on the lab PC, and the phone's sign-in must reach Keycloak at the lab PC's network address. Campus Wi-Fi often blocks traffic between devices (client isolation).
  • Expo's tunnel mode works around this, but needs internet access and a third-party relay.
  • Expo Go also runs only projects built for the SDK versions it supports, usually the most recent ones. A phone with an updated Expo Go may refuse a project pinned to an older SDK.
  • Decisions needed:
    • a lab Wi-Fi access point without client isolation (a small purchase), or USB connection, or installing development builds as APK files;
    • choosing and testing the SDK version just before each semester.

9.3 Assessment load in weeks 7 and 13.

  • Week 7 holds practical test 1 of both CSE-4772 and CSE-4782, and the Capstone I proposal defence.
